## 1. Задача и счёт (коротко; подробности в приложении)

Decentrathon 6.0, Soup Kernel Challenge. Фиксированный `soup train` (soup-cli 0.77.0): Qwen2.5-1.5B-Instruct, NF4 (bitsandbytes, double quant), compute fp16, LoRA r=16 alpha 32 dropout 0,05 только на q_proj и v_proj, batch 4, ≤ 512 токенов на строку, 64 шага, AdamW torch, cosine, TRL SFTTrainer (Soup: RewindSFTTrainer) с loss только по ответу; каждый шаг entropy и token accuracy от TRL и per-row loss в `rewind.jsonl`. Харнесс на Kaggle T4 (sm_75, 70 Вт, PCIe Gen3 x16 ~12 ГБ/с pinned, хост 4 vCPU) запускает базу и решение в свежих процессах, мерит стену всей команды снаружи (от старта процесса до сохранённого адаптера, компиляция Triton с пустым кэшем входит) и пик nvidia-smi раз в 100 мс. Наш пакет `solution/` (`apply()` до сборки модели) патчит что угодно в transformers/peft/bnb/trl/Soup. Матмулы в cuBLAS (Triton 3.6 на sm_75 не использует тензорные ядра), свои Triton-ядра для поэлементных операций, редукций, распаковки, loss; доля своих ядер ≥ 5 % времени обучения с шага 3 (ядра внутри CUDA graphs не считаются). Харнесс делает `torch.cuda.synchronize()` в начале и в конце каждого шага (колбэк).

Баллы: 20 за все 10 проверок (иначе 0); скорость 35·ln(s)/ln(s_best); память 30·ln(m)/ln(m_best); README 15. s и m — отношения база/решение. Проверки качества: кривые loss/entropy/accuracy/rewind по шагам — средняя относительная разница ≤ 3 %; eval loss (считается чистыми transformers+peft по адаптеру, без нашего кода) ≤ 0,5 %; жюри гоняет базу и решение по 2 раза на скрытых строках с другим seed. Соперник заявил 29 с / 937 MiB при базе ~85 с (s 2,93, m 15,3): по формуле он 35 + 22,4 = 57,4 без README; мы на 371 MiB берём все 30 за память, точка равенства с ним ≈ 36,6 с; на 35 с мы +1,5 балла, на 33 с +3,4 (если он не улучшится). У остальных команд, по нашим сведениям, память ≥ 600 MiB.

Вопрос 4: Какие потребители (consumers) строго требуют полные `outputs.logits`, а какие могут работать с компактными статистиками? Ответ организатора: Полные логиты строго никому не нужны, требуются только вычисленные из них результаты. Soup берёт из логитов три вещи: 1) Loss и градиент (можно считать fused-кернелом по чанкам без хранения всего тензора в памяти); 2) метрики TRL — энтропия и точность (скалярные числа); 3) лог Soup — per-row loss (короткий вектор). Вместо тензора `[batch, length, 152000]` можно передавать эти компактные значения при условии, что они совпадают с базой в пределах 3% и считаются на тех же токенах (маска `-100`, сдвинутая на один).

Вопрос 5: Мы ускорили вычисление энтропии примерно в 10 раз, но общее время обучения почти не изменилось. Можете показать профиль запуска и указать конкретную функцию, оптимизация которой даст наибольшее сокращение общего времени обучения? Какие затраты для Qwen2.5-1.5B на T4 самые значимые после реализации chunked loss, декодирования NF4, RMSNorm и LoRA fusion: backward через замороженные NF4-проекции, конвертации FP32↔FP16 или attention? Ответ организатора: В первую очередь профилируйте backward-проход через замороженные проекции: он всё ещё включает распаковку NF4 и GEMM градиентов по входу. Затем проверьте повторные конвертации типов (dtype conversions) и `lm_head`. Attention стоит приоритизировать только в том случае, если ваш текущий профиль показывает, что он занимает существенную долю времени выполнения.

## Ответы организаторов на наши четыре вопроса (30 октября, вечер)

1. Процесс-помощник для компиляции Triton: **нельзя**, это фоновый процесс (запрет из раздела «обход замера»); компилировать в потоке того же процесса или синхронно; пустой кэш и учёт времени запрет не снимают. Действие: прогрев возвращается в поток внутри процесса, код помощника убрать до сдачи.
2. Эмбеддинг и lm_head в pinned-памяти хоста со стримингом головы каждый шаг: **можно** как собственный CPU-оффлоад; копии и синхронизация в замере, значения, dtype и обязательные выходы сохраняются.
3. Хвост выравнивания до кратного 16: **можно** как внутреннее выравнивание вычислений; фиктивные позиции не должны влиять на реальные токены, attention, loss, метрики, rewind и учитываемое число токенов (тест на это добавляет T12).

```
"""Our solution: Triton kernels and patches that make the fixed `soup train` run on a Kaggle T4
faster and lighter without changing what it trains.

The harness imports this package and calls `apply()` once, in the same process as `soup train`,
before Soup builds the model and the trainer. Every patch is a class-level method replacement looked
up at call time, guarded so that anything that is not the real CUDA Qwen2 training step (Soup's
regression tests with fake modules, eval, generation, CPU) takes the original code path.

Modules:
- fused_ce.py: lm_head + cross-entropy + TRL metrics without the (B, T, V) logits (own kernel);
- trainer_patch.py: TRL's compute_loss logging the same metrics from the fused head, and Soup's
  rewind recorder fed through its own hook for steps without logits;
- unpad.py: the layers run on the packed real tokens of the batch, attention per row;
- mlp16.py: the MLP's gate/up/SwiGLU in half storage (uses the kit's example SwiGLU kernel, which
  does not count as ours);
- embed16.py: the tied embedding / lm_head weight back in fp16 after Soup's setup;
- rmsnorm.py: RMSNorm and residual-add + RMSNorm in one Triton kernel each way (own kernels);
- nf4.py: NF4 dequantization in one Triton kernel, used by bitsandbytes' MatMul4Bit (own kernel);
- rope.py: rotary embedding of q and k in one Triton kernel each way (own kernel);
- fused_proj.py: q+k+v in one GEMM with LoRA by addmm, attention in half, gate+up in one GEMM;
- offload.py: the MLP's saved gate|up to pinned host memory on a side stream with events (prepinned
  slabs), or recomputed in the backward (SOUP_SOLUTION_MLP_MEMORY=recompute: +50 ms per step for
  24 MiB on the T4, so off by default);
- alloc_watch.py: the caching allocator's retries and segment frees, logged once per run;
- head_stream.py: the tied embedding / lm_head weight in pinned host memory for the whole run,
  the head computed in one streamed pass over the vocabulary (own kernels); switched on from
  fused_ce.patch_qwen2_causal_lm (SOUP_SOLUTION_HEAD_STREAM=0 turns it off);
- weight_stream.py: the layers' 4-bit weights in pinned host memory, a ring of K layers on the GPU;
- warmup.py: the kernels compiled by a background thread while Soup loads the model (triton's own
  hash started with apply());
- startup.py: apply()'s imports without work the run does not use (trl's second metadata scan,
  scikit-learn, wandb, bitsandbytes' Inductor), the imported objects frozen for the garbage
  collector, the tokenizer hashed fast by datasets in Soup's setup; a first-step phase mark; a
  profile of the trainer build (diagnostics);
- phases.py: wall-clock marks of the run's phases in the log;
- diag.py: diagnostics of a run (SOUP_SOLUTION_DIAG=1 only): memory at the marks, a PCIe probe,
  an allocation snapshot of one step, a chrome trace of two steps.

Switches (environment, for experiments): SOUP_SOLUTION_CE_CHUNK (rows of logits per chunk, default
512), SOUP_SOLUTION_UNPAD=0, SOUP_SOLUTION_MLP16=0, SOUP_SOLUTION_EMBED16=0, SOUP_SOLUTION_RMSNORM=0,

SOUP_SOLUTION_REBUILD_X16=0, SOUP_SOLUTION_CARRY_RESIDUAL=0, SOUP_SOLUTION_HEAD_STREAM=0
(SOUP_SOLUTION_HEAD_ROWS, SOUP_SOLUTION_HEAD_SLOTS, SOUP_SOLUTION_HEAD_PREFETCH=norm|embedding|head),
```

## Внешнее ревью 2 (GPT-6 Astra Pro, 31 октября ~11:00; бриф `docs/briefs/astra-brief-2-2026-10-31.md`, ответ целиком `docs/briefs/astra-answer-2-2026-10-31.md`)

Вопрос брифа был один: из чего собрать −60…−100 мс GPU на длинном шаге при 70 Вт и 400 MiB, чтобы выйти на 30 с. Ответ: не из чего. [A] = утверждение Астры (расчёт или инженерная гипотеза, на T4 не проверено), [V] = наше измерение.

**Главный вывод.** [A] 30 с при 400 MiB снять с обязательной цели: надёжного набора независимых улучшений на 60–100 мс GPU/шаг нет; виден пакет на 20–40 мс критического пути при N≈830, если удачно пройдут attention backward и int8, и их выигрыши частично перекрываются (ускоренный backward начинает ждать PCIe). От 42,7 с ближайшие проверяемые изменения ведут к 35–38 с в сопоставимой сессии; 33–35 с это оптимистическая цель после CPU/startup-работ, не доказанный пол. Её арифметика: −0,8 с на границе, −0,6 с на коротких CPU-bound шагах, −30 мс на остальных 51 шагах дают цикл ~23,4 с, то есть ~35,9 с стены при стартовом бюджете 12,5 с. Горячие прогоны считать отдельно.

**Поправки к постановке.** [A] Средний шаг (N≈830: 4,93 TFLOP GEMM) и длинный (N=2048: 12,17 TFLOP, 358 мс одних GEMM при 34 TFLOPS) имеют разные пределы: 0,26–0,28 с это цель среднего шага, не каждого. [A] CPU всё ещё важен, но адресно: 17 мс пустой очереди перед оптимизатором это до 1,09 с за прогон; синхронизация метрик перед backward мешает заранее поставить backward в очередь; после ускорения GPU часть GPU-bound шагов станет CPU-bound. Убирается задержка постановки, не математическая зависимость от dh.

**1. NF4 внутри MMA.** [A] Инструкция `mma.sync.m16n8k8` на sm_75 есть, но стандартный MMA-pass Triton 3.6 ниже sm80 выключен, а `inline_asm_elementwise` не раскладывает элементы по lane как MMA-фрагмент: раскладку, обмен и shared контролировать вручную. Эскиз: CTA 64×128×32 (4 warps, 24 КиБ shared на две стадии), decode раз на CTA в shared, 64 fp32-аккумулятора на поток; без cp.async (Ampere) переносы конкурируют с MMA. Decode повторяется между M-тайлами (13 раз на элемент веса при 832 токенах и BM=64). Правильное сравнение Δt = t_dequant + t_cuBLAS − t_fused: при 28–34 TFLOPS у cuBLAS точка безубыточности полного fused-пути 23,2–27,2 TFLOPS; первый прототип скорее ниже. Численно decode побитовый, GEMM с другим порядком накопления нет. Оценка: предтест обычного fp16 MMA 4–6 ч, полная работа 40–80 ч, вероятность положительного net 30–40 %, шанс получить 60–100 мс очень низкий. **Не основное направление перед сдачей.**

**2. Attention backward.** [A] Лучший короткий эксперимент: батчевые cuBLAS GEMM плюс свои ядра softmax/mask/dS с выбором пути по форме. Пять произведений (S=QKᵀ, dP=dO·Vᵀ, dV=Pᵀ·dO, dQ=dS·K, dK=dSᵀ·Q), при L=208 2,66 GFLOP на слой (0,18 мс при 15 TFLOPS). Путь: forward не трогать, Q/K/V восстановить как сейчас, S с fp32-выходом (`torch.bmm(..., out_dtype=torch.float32)` в torch 2.11), своё ядро маска→P, четыре GEMM, своё ядро dS = P⊙(dP−δ), δ = Σ P·dP, свести 6 query-голов на KV-голову. Память: один fp16 и один fp32 буфер 4·12·L²: 12 MiB при L=208, 18 при 256, 72 при 512; при L≤256 влезает в простаивающий буфер распаковки NF4 (26,25 MiB). Гипотеза: 0,25–0,50 мс на слой вместо 0,82 при L≈208, то есть 8–16 мс за 28 слоёв на подходящем шаге; при L=512 преимущества не ждать. Фильтр: N≥600, L_max≤256, умеренный паддинг. FMA-attention на Triton без тензорных ядер (3–4,6 TFLOPS fp32) выигрыша не даст; свой tensor-core attention 24–48 ч ради 1,35–1,5× (открытая реализация для Turing). Отдано подчату E1+A2.

**3. Selective recompute.** [A] Таблица хранения (байт на токен на слой; за 28 слоёв при 830 токенах): Q 3072 (68 MiB), K и V по 512 (11 MiB), O 3072, LSE 48 (1 MiB), U=o_proj(O) 3072, s=x+U fp32 6144 (136 MiB), rstd 4. Хранить K/V бессмысленно, пока Q требует повторного QKV-прохода; сохранённый LSE не отменяет пересчёт O, потому что efficient-attention backward читает O для δ. При нынешнем backward дополнительная экономия 0–3 мс/шаг, не 16–35. Новый вариант появляется вместе с math-backward из п. 2: оффлоадить на хост только U fp16 (H2D 5,95 мс при 830 токенах), восстановить s = x + U прежней fp32-операцией, в новом backward считать δ = Σ P·dP без O: отпадают повторный attention forward и повторный o-GEMM (8–11 мс/шаг), net 0–5 мс, при 2048 токенах исчезает. Второй этап после п. 2.

**4. SwiGLU и поэлементные.** [A] 17 мс на SwiGLU правдоподобны (16·N·I·28 = 3,33 ГБ за шаг, 14,5 мс при 230 ГБ/с): это не плохое ядро. Убрать можно только эпилогами собственного GEMM (SwiGLU в эпилоге forward gate/up ~3,6 мс; SwiGLU-backward в эпилоге backward down ~3,6 мс), то есть тем же проектом MMA из п. 1. SwiGLU-backward с распаковкой down не сливается (между ними GEMM). Нормы сразу в раскладке потребителя: ~2,5 мс за 57 норм, если исчезает отдельная копия. Без своего GEMM остаётся 1–4 мс/шаг.

**5. Энергия и fp16-аккумуляция.** [A] Из перестановки ядер воспроизводимого рычага больше 2 % шага не видно: порядок задан зависимостями, dequant и поэлементные уже перемежаются с GEMM, ускорение одного участка повышает среднюю мощность соседнего. В бюджет 0. fp16-аккумуляция нигде заранее не укладывается в допуски (down с K=8960, градиент gate/up с K=17920, знакопеременные суммы под GradScaler); проверенный backward-only int8 предпочтительнее.

**6. Голова.** [A] Потолок экономии копий: 13 бит −7,29 мс, 11,3 бита −11,43 мс на шаг при 12 ГБ/с; на горячем шаге с 5,6 мс ожидания это не вернётся в стену целиком: прогноз 3–8 мс/шаг, иногда меньше. [V] Наш 12-битный кодек E1: ожидание головы 9 → 2 мс/шаг, в стене −0,07…−0,24 с за +2 MiB (выключен). [A] Ранних свободных слотов в кольце по типам в середине forward нет (каждый слот ждёт следующий слой); единственная точка заимствования это последний слой после последней распаковки gate/up, с событием окончания чтения и без автопрефетча стримера: 0–2 мс/шаг, не масштабируется с N. Для раннего размещения 314–362 MiB сжатой головы ёмкости нет.

**7. int8 до стены.** [A] Предел PCIe backward: при 830 токенах возврат gate/up 0,833 ГБ + residual 0,143 + NF4 0,65 = 135,5 мс при 12 ГБ/с; при 2048 токенах 254,8 мс. Новый механизм: в int8-пути gate/up освобождается после квантования dgate/dup в отдельный g8, не дожидаясь GEMM, поэтому префетч gate/up следующего по backward слоя стартует раньше (при 830 токенах окно порядка миллисекунды на слой существенно); если g8 алиасит gate/up, раннее освобождение невозможно. Порядок копий по ближайшему потребителю: сначала NF4-вес следующей распаковки, затем gate/up следующего слоя; разбиение activation-copy на части 4–8 MiB только после трассы (CPU-вызовы); stream priority это подсказка, не гарантия. Второй полный activation-slot (28 MiB при 832, 70 при 2048) при лимите 400 MiB не окупается. До стены при N≈830: 8–20 мс, из них новое расписание поверх готового int8 0–8 мс. Attention и int8 полностью не суммируются (оба сокращают compute одного backward, под которым прячутся те же копии). У нас int8 выключен до ответа организаторов.

**8. Итоговая таблица Астры** (экономия при N≈830 / риск / часы): batched-GEMM attention backward 8–16 мс на подходящих длинах / средний / 4–8; int8 MLP backward с расписанием 8–20 мс критического пути / средний / 2–5 поверх готового; сжатие головы 3–8 мс / нет при точном decode / уже сделано (E1: меньше); head-prefetch в освобождённые слоты 0–2 мс / средний (гонки) / 2–4; оффлоад только U + backward без O 0–5 мс дополнительно / средний / 4–8 после math-backward; остаточные слияния поэлементных 1–4 мс / низкий / 3–6; NF4+MMA в план 0 (удачный полный путь 10–25 мс) / средний / 40–80; свой tensor-core attention 4–8 мс вместо math-backward / 24–48; перестановка ядер 0; удаление CPU-хвоста перед optimizer до 17 мс стены на всех шагах / низкий–средний / уже у C1 и B1. Нельзя складывать: NF4+MMA и int8 заменяют одни и те же GEMM; новый attention и int8 делят один PCIe-limited backward; ранний head-prefetch и сжатие убирают одно ожидание; SwiGLU-эпилоги требуют того же GEMM, что и MMA.

**Её выбор на оставшиеся часы:** два ограниченных GPU-эксперимента (batched-GEMM attention backward на фактических векторах длин; раннее освобождение gate/up после int8-quantize, если int8 разрешат), продолжить CPU/startup/codec, NF4+MMA только как короткий предтест; если attention не даёт хотя бы ~8 мс на подходящем шаге, а int8 упирается в PCIe, прекратить поиск −60…−100 мс и вложить время в устойчивость, финальные прогоны и README.

**3. CUDA graphs.** [A] Разрешение снимает больше CPU-обвязки, чем слияние autograd-нод, но выгода графов это launch overhead, не меньше GEMM; GPU-bound длинные шаги много не дадут. Входами графа должны быть и меняющиеся параметры (начало чанка, scales, online-max/sum, маски, аккумулятор dh). Ловушка PyTorch 2.11: `torch.cuda.graph.__enter__` делает `synchronize`, `gc.collect`, `empty_cache` и `_host_emptyCache`: захват на каждом новом размере осушает очередь, чистит кеши GPU и pinned-памяти, бьёт по проверке 9 и по стене; private pool графа живёт, пока жив граф; capture нельзя совмещать с параллельными CUDA-операциями потока прогрева. Dropout оставить прежним (свой RNG запрещён), первый прототип без dropout. Зачёт 5 % только для ядер вне графа: целиться в ≥ 7 % на стресс-формах. **4. [V] C1 (заметка, раздел 7): рост сидит в длинных GPU-bound шагах, строки жюри на 10–20 % длиннее публичных, при равном числе токенов наш шаг относительно базы теряет 6–12 %. Законные способы: меньше пересчёта за память, int8, устранение неперекрытых копий, меньше лишних записей; искусственные паузы и power limit не рассматривать.

## Switches (all off by default until measured)

- SOUP_SOLUTION_EMBED_ASYNC (load_stream.py, head_stream.py): the embedding's job returns its pinned
  buffer and a thread casts the slice into it (`copy_`, the kernel `.to()` runs); joined before the
  load returns. Bit-equal (tiny Qwen2 with and without the pinned copies, failing thread, real model).
- SOUP_SOLUTION_LOAD_PREAD (load_pinned.py, load_stream.py): the pinned staging reads each tensor's
  bytes with `preadv` from the file (byte ranges from the safetensors header, files recorded from
  `safe_open` in Soup's setup) instead of faulting in the mmap; the embedding fill too (32 MB chunks
  into a scratch, cast into the buffer). Locally the real load's staging 1.1-2.3 s -> 0.33 s, the
  tensor loop 1.6-3.0 s -> 0.77 s. Bit-equal (tiny and real model).
- SOUP_SOLUTION_TRITON_KEY=light (warmup.py): triton's cache key with libtriton.so named by size,
  mtime and inode instead of a sha256 of 415 MB (the harness gives every run an empty
  TRITON_CACHE_DIR; the key only names its entries); 0.20 s -> 0.002 s locally.
- SOUP_SOLUTION_ENTRY_POINTS (startup.py): `importlib.metadata.entry_points()` read once from apply
  begin (bitsandbytes, fsspec, Soup's plugins asked three times, ~65 ms each on Kaggle) and answered
  with `select()` while sys.path is unchanged (as the allowed packages_distributions cache).
- SOUP_SOLUTION_LOAD_CODE_TABLE (load_stream.py): bitsandbytes' NF4 table built once per load and
  cloned on the GPU for every weight (same values, own tensor per quant state).
- SOUP_SOLUTION_EARLY_PROBES=p2p (trainer_build.py): only accelerate's nvidia-smi check in the thread.
- Measuring only: SOUP_SOLUTION_HELD_ENCODE (trainer_build.py), SOUP_SOLUTION_LAUNCHERS_EARLY
  (warmup.py), SOUP_SOLUTION_WARMUP_START=setup (warmup.py).

# Оптимизация QLoRA на Tesla T4: что ещё реально может дать 32–35 с

## Вывод и приоритеты

При ваших текущих 43,4 с узкое место уже не похоже на «ещё одно более быстрое элементwise-ядро». Наиболее перспективный путь к 35–38 с — **потратить свободную GPU-память на устранение recompute и неперекрытого PCIe**, а затем выжать несколько процентов из cuBLAS за счёт формы GEMM и пропуска математически ненужных ветвей backward. Цель 32–35 с выглядит возможной, но нижняя граница, скорее всего, потребует либо разрешённого INT8 backward, либо собственного Turing Tensor-Core GEMM; одними RMSNorm/SwiGLU/копиями я бы на дополнительные 8–11 с не рассчитывал.

Самый сильный короткий эксперимент — **оставить fp16 `lm_head` резидентной**. Ваш текущий пик 371 MiB + 445 MiB ≈ **816 MiB**, то есть прямо попадает в желаемые 600–900 MiB. Это устраняет 445 MiB H2D на каждом шаге; при вашем уже измеренном остаточном ожидании 6–20 мс это означает **0,38–1,28 с за 64 шага**, не считая возможного уменьшения contention с остальными D2H/H2D. Для PCIe Gen3 x16 NVIDIA приводит примерно 12 GB/s для pinned memory, что согласуется с вашим наблюдением. citeturn798833search2turn798833search4

Второй по привлекательности вариант — **не хранить все attention-активации, а сохранить именно post-RoPE Q/K/V для recompute-backward**. У Qwen2.5-1.5B 28 слоёв, `hidden=1536`, 12 Q-heads, 2 KV-heads, head dim 128. citeturn920378search0turn920378search10 При 830 токенах один слой Q+K+V в fp16 — примерно `830 × (1536+256+256) × 2 = 3.24 MiB`; все 28 — около **91 MiB**. Если ваш attention recompute действительно повторяет RMSNorm→QKV→RoPE, эти 91 MiB потенциально убирают повторный QKV GEMM и часть поэлементных операций. По вашему собственному бюджету я бы ожидал **8–15 мс/шаг**, то есть **0,5–1,0 с/прогон**; это оценка, а не опубликованный T4 benchmark. Идея соответствует selective recomputation: Korthikanti et al. показывают, что хранить небольшой набор дорогих для recompute активаций значительно выгоднее полного checkpoint/recompute, хотя их цифры получены на крупных A100-кластерах, а не T4. citeturn337321academia7

## Turing Tensor Cores, W4A16 и cuBLAS

Главное подтверждение вашего наблюдения: начиная с Triton 3.3 upstream deliberately перестал ускорять `tl.dot` через MMA на compute capability ниже 8.0. Свежий разбор vLLM на реальной T4 показывает, что Triton 3.7.1 для fp16 dot генерирует `fma.rn.f32`, а Triton 3.1 генерировал `mma.sync`; для attention это дало экстремальный разрыв — например, Qwen2.5-1.5B 8k prefill около 10,2 с против 1,1 с у Turing-capable tensor-core backend. citeturn914405search0

При этом само железо T4 совершенно точно поддерживает `mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32`; этот exact PTX присутствует в NVIDIA CUTLASS sm75 primitives. citeturn755369search3 ExLlamaV3 Turing fork также использует именно `m16n8k8` для sm75. citeturn630822search0 Llama.cpp на Turing разбивает более новый Ampere `m16n8k16` на две `m16n8k8`. citeturn630822search6

Есть особенно важная свежая находка: community fork **triton-turing** восстановил sm75 MMA, сделал software pipeline `ld.global → st.shared → bar.sync`, добавил Turing-specific configs и заявляет для FP16 GEMM **87–89% скорости cuBLAS** на Titan RTX sm75; INT4 tensor-core kernel достигает до **258 TOPS** и примерно в 2,1–2,5 раза быстрее его INT8 path. Это не T4 и не NF4 W4A16, поэтому эти цифры нельзя напрямую переносить на ваш workload, но это сильное доказательство, что ограничение — compiler path Triton, а не Turing ISA. citeturn914405search5turn630822search8

Для **stock Triton 3.6** путь через `tl.inline_asm_elementwise` намного менее привлекательный, чем кажется. API допускает inline PTX, но он обрабатывает группы элементов, причём документация прямо говорит, что точный набор элементов на invocation не специфицирован. citeturn771363search0 Уже существующий Triton issue описывает проблему: layout dot-operands не propagates через `inline_asm_elementwise`, из-за чего fragment-level операции перед `tl.dot` становятся медленными. citeturn771363search4 Поэтому написать одиночную `mma.sync` инструкцию несложно; сложно вручную построить правильные sm75 warp fragments, shared-memory swizzle, `ldmatrix`, register ownership и accumulation layout, оставаясь внутри обычной Triton Python модели. Я не нашёл надёжного публичного примера полного sm75 GEMM на stock Triton 3.6, реализованного только через `tl.inline_asm_elementwise`.

W4A16 тоже надо разделять на два разных случая. Turing имеет **integer** tensor-core instructions `m8n8k16` INT8 и `m8n8k32` INT4, но они требуют integer activations; NF4×FP16 не может непосредственно идти в INT4 MMA. citeturn630822search8 AWQ-подобные kernels делают другое: распаковывают 4-bit weights, применяют scale/zero, превращают их в fp16 в register/shared и после этого кормят fp16 MMA. Код AWQ показывает именно эту схему dequant→fp16 shared→`ldmatrix`→MMA. citeturn630822search1 Для NF4 вместо `(q-zero)*scale` нужна LUT NF4 и double-quant absmax; официальный bitsandbytes код подтверждает LUT-based NF4 decode. citeturn706614search0turn706614search1

То есть перспективный собственный NF4 GEMM на T4 выглядит так: packed NF4 остаётся в global → byte/nibble decode → LUT+absmax → fp16 fragments в shared/register → `m16n8k8` → fp32 accumulate. Это технически возможно; ExLlama/Humming/AWQ показывают все необходимые части по отдельности. Но без восстановления compiler MMA layout или CUDA C++ это не проект на 4–8 часов. Humming, например, поддерживает weight-only low-bit FP16 GEMM начиная с SM75 и позиционируется как специализированная JIT GEMM library, что косвенно показывает объём специализированного machinery, необходимого для конкурентной реализации. citeturn630822search9

По cuBLAS ваши основные размеры уже благоприятны: 1536, 8960, 256, 151936 кратны 8. NVIDIA для fp16 рекомендует, чтобы наиболее быстро меняющиеся dimensions/leading dimensions были выровнены на 16 байт, то есть 8 fp16 элементов. citeturn798833search0turn798833search1 Поэтому я бы не тратил время ещё на алгоритмы cuBLASLt — вы их уже перебрали. Стоит проверить только **runtime M**, то есть число реальных токенов после depadding. Внутренний padding `M→ceil(M/8)*8` добавляет максимум семь фиктивных строк и иногда переводит GEMM в лучшее kernel family; это особенно дёшево при M≈100–200. Публичные T4 GEMM данные показывают сильную зависимость достигнутой производительности от формы: примерно 14,8 TFLOPS для 1024³ и около 20–27 TFLOPS для более благоприятных rectangular/large shapes. citeturn329695search5

## Математически ненужный backward и attention

Для LoRA только на q/v backbone полностью frozen, но обычно нельзя просто отказаться от `dX`: gradient hidden state нужен для LoRA более ранних слоёв. QLoRA именно так и работает — backpropagates через замороженную 4-bit модель к trainable adapters. citeturn337321academia8 Однако **первый transformer block — исключение**.

Пусть первый блок имеет стандартную структуру
`u = x + Attn(RMS(x))`,
`y = u + MLP(RMS(u))`.
Чтобы получить q/v LoRA gradients первого блока, нужно донести `dy` назад через последний MLP до `du`, затем через `o_proj` и attention получить `dQ` и `dV`. Но после вычисления q/v LoRA dA/dB вам больше не нужен `dx`, потому что embeddings frozen и перед первым блоком нет trainable parameters. Следовательно, в первом блоке можно не вычислять `dK`, не выполнять base Q/K/V input-gradient GEMMs и не выполнять окончательный RMSNorm input backward. Это точная оптимизация, а не аппроксимация. Потенциальный выигрыш умеренный, потому что затрагивает лишь 1/28 модели, но отношение «часы/выигрыш» хорошее.

В последнем слое появляется другая возможность. Cross-entropy выдаёт нулевой gradient logits для позиций с `ignore_index`. Пока backward идёт только через positionwise `final RMSNorm` и последний MLP, эти нулевые строки остаются нулевыми. Поэтому эти операции можно выполнить лишь для label positions. После прохождения attention градиент распространяется на key/value позиции и sparsity исчезает. Отсюда точная граница оптимизации: **final norm + последний MLP + часть query-side последнего attention backward**. Если доля обучаемых токенов `f`, FLOP last-MLP-backward примерно масштабируется как `f`, то есть theoretical saving этого конкретного блока ≈`1−f`.

Для attention формулы дают более тонкий skip:
`dV = Pᵀ dO`,
`dP = dO Vᵀ`,
`dS = P ⊙ (dP − rowsum(dP⊙P))`,
`dQ = dS K`,
`dK = dSᵀ Q`.
Если `dO[q,:]=0` для unlabeled query q, то строка `dQ[q,:]` точно нулевая; однако `dK` и `dV` собирают contributions от всех ненулевых query и нужны для propagation к более ранним токенам. Поэтому разделение dQ и dK/dV полезно прежде всего в **последнем слое** и в **первом слое**, но по разным причинам.

По пункту «есть ли готовый attention backward на T4 быстрее PyTorch `_efficient_attention_backward` для ваших 4×100–500, d=128, causal, GQA 12/2?» надёжного публичного результата я не нашёл. PyTorch sm75 backend уже содержит специализированные CUTLASS kernels с tile families 64×64 и 32×128 для fp16 sm75. citeturn801057search3 cuDNN SDPA здесь не альтернатива: текущий cuDNN SDPA требует SM80+. citeturn801057search4 Свежий T4 опыт vLLM показывает обратное: обычный Triton attention на современных Triton версиях катастрофически проигрывает tensor-core CUDA backend из-за отсутствия sm75 MMA. citeturn755369search0 Поэтому ваш уже отвергнутый batched-cuBLAS + custom softmax результат выглядит правдоподобно, и я бы attention kernel не ставил в 4–8-часовой план.

## Память, PCIe, startup и power cap

Ваши 371 MiB — необычно низкий footprint, поэтому оптимум находится не в дальнейшей экономии памяти, а в **маржинальной ценности MiB**.

Для `lm_head`: `445 MiB / (6–20 ms saved)` даёт примерно **22–74 MiB на 1 мс/шаг**. Для layer inputs около 70 MiB устраняют ~140 MiB H2D, но почти всё это у вас уже скрыто compute; вероятный выигрыш лишь несколько миллисекунд. Для post-RoPE QKV около 91 MiB могут устранить реальный recompute GEMM, поэтому это, вероятно, лучший **compute-saving per MiB** объект. Полный gate/up retention стоит порядка 0,8 GiB и потому невыгоден; selective retention нескольких слоёв разумнее.

Из этого следует рекомендуемая memory layout при ceiling 900 MiB: **371 + 445 head + ~70 MiB layer inputs = ~886 MiB**. Альтернатива, если QKV retention benchmark окажется сильнее input-offload elimination: **371 + 445 + ~91 ≈907 MiB**, чуть выше вашей мягкой цели, но всё ещё чрезвычайно далеко от базовых 14 GiB. Если 900 MiB жёстко, можно хранить QKV лишь у 24–25 слоёв или не держать несколько MiB служебных buffers одновременно.

Полностью резидентные NF4 требуют примерно ещё 619 MiB сверх вашего текущего 25,7 MiB ring и поднимают footprint примерно до 990 MiB. Это хуже head по двум причинам: ваш NF4 PCIe уже хорошо перекрывается compute, а head имеет измеряемый 6–20 мс residual bubble. CUDA Best Practices прямо рекомендует уменьшать transfer и объединять небольшие копии, но wall-clock выигрыш определяется именно неперекрытым хвостом, а не суммарными GB/s. citeturn798833search2

Для copy ordering я бы использовал один принцип: **earliest-deadline-first по consumer**, а не FIFO по типу буфера. Head chunk, который нужен текущему vocab chunk, должен иметь priority над NF4 слоя N+2; gate/up возврат для слоя N — над prefetch более дальнего слоя. CUDA позволяет H2D/D2H overlap с compute на разных streams. citeturn798833search4turn798833search6 У T4 нет причин ожидать магического выигрыша от большого числа streams; power и copy-engine contention быстро съедят benefit.

По startup есть два реально подтверждённых направления. Во-первых, Transformers 5.16.1 действительно имел import chain, где даже tokenizer/config paths затягивали `torch` и `sklearn`; измерения показывали 2,5–3,0 с вместо 0,58 с в одном тесте и разницу порядка 4,5 с на Colab при полном model-load сценарию. citeturn872934search2 Вам нельзя скрыть `torch`, но можно **не импортировать TRL/PEFT до момента, когда GPU уже занят загрузкой/квантованием**, и таким образом перекрыть часть Python import latency реальной GPU работой. Transformers уже построен вокруг lazy import machinery, поэтому лучше патчить конкретные eager access paths, а не создавать fake modules. citeturn872934search0turn872934search1

Во-вторых, модельный loader. Исследование fastsafetensors показывает 4,8–7,5× ускорение больших model loads за счёт group transfers и direct device materialization, но это отдельная библиотека и другие масштабы. citeturn550677academia9 Более переносимый инженерный результат: loader с двумя pinned staging buffers по 64 MiB перекрывал CPU materialization и H2D и существенно обгонял pageable mmap на H200/5090. citeturn550677search8 На T4 потолок PCIe намного ниже, поэтому простой pipeline `mmap read → pinned A/B → async H2D → quantize(stream)` особенно логичен. Однако для ваших 2,5 GB и уже 3,2 с total я бы ставил ожидаемый выигрыш только **0,2–0,7 с**, пока profiler не покажет, что файл действительно читается последовательно и page cache не является bottleneck.

По power cap есть надёжное подтверждение, но мало actionable kernel tricks. T4 специфицирован на 70 W и 65 FP16 TFLOPS peak. citeturn329695search1 NVIDIA инженер отдельно пишет, что при непрерывном matrix multiply T4 power-caps и около 24 TFLOPS является нормальным устойчивым результатом. citeturn329695search0 NVIDIA TensorRT guide предупреждает, что вставка gaps может временно поднять clock, но это создаёт завышенный benchmark throughput и не улучшает работу при полном load. citeturn329695search2 Поэтому я не нашёл оснований специально вставлять memory-bound kernels между GEMM. Если эти операции всё равно нужны, порядок «GEMM → обязательный bandwidth kernel → GEMM» можно измерить, но намеренное охлаждение SM почти наверняка проиграет.

INT8 действительно потенциально энергоэффективнее: T4 имеет заявленные 130 INT8 TOPS против 65 FP16 TFLOPS. citeturn329695search1 Но в вашем случае практический факт уже сильнее литературы: готовый dX MLP INT8 даёт −0,55 с. Поскольку вы просили не предлагать уже сделанное, я считаю его не новым пунктом, а просто важным ориентиром масштаба: один sanctioned low-precision GEMM path закрывает заметную часть разрыва.

## Топ по выигрышу на час реализации

**Первое — резидентный `lm_head`.** Сразу выделить постоянный fp16 buffer до тренировочного цикла, один раз заполнить его после model load, переключить chunked loss на device slices вместо H2D staging, убрать связанные events/copies, проверить peak `nvidia-smi`. Ожидаемый результат: −0,4…−1,3 с за 30–60 минут работы.

**Второе — сохранить post-RoPE Q/K/V для recompute.** Добавить ring/arena размером около 3,3 MiB на слой; forward сохраняет fp16 Q,K,V сразу после RoPE; backward attention берёт их напрямую и пропускает RMSNorm→QKV→RoPE recompute. Сначала сделать для одного слоя и замерить разницу kernel timeline, затем включить все слои. Контроль: bitwise/close dLoRA и loss. Ожидаемо −0,5…−1,0 с за 2–4 ч.

**Третье — GPU-resident layer inputs.** Выделить contiguous `[28, max_tokens,1536]` fp16 arena или compact variable-token offsets; вместо D2H forward оставить device pointer/slice; backward читать напрямую; удалить corresponding H2D events. Это около 70 MiB при среднем batch и хороший кандидат, если head residency оставляет место. Ожидаемо −0,06…−0,26 с за 1–2 ч.

**Четвёртое — M-rounding GEMM probe.** Не переписывать модель целиком: сделать microbenchmark на реальных M из всех 64 шагов для `M`, `ceil8(M)`, `ceil16(M)` на 1536×1536, 1536×8960, 8960×1536 и QKV fused shapes, используя ровно текущий addmm/cublas path. NVIDIA рекомендует fp16 alignment в 8 элементов, но конкретный выигрыш надо измерить на T4. citeturn798833search0turn798833search1 Если есть стабильные >3%, внедрить padded scratch rows и отбросить tail. 2–4 ч.

**Пятое — truncated backward первого блока.** В custom autograd первого layer после получения `dQ`, `dV` вычислить q/v LoRA dA/dB и завершить backward, не запуская dK и Q/K/V base-input gradients/RMSNorm input gradient. Отдельно убедиться, что upstream gradient для attention уже включает last-MLP residual branch. 3–5 ч; выигрыш небольшой, но гарантированно не меняет forward.

**Шестое — label-compacted last MLP/final norm.** На выходе loss сохранить sorted/packed indices с ненулевым gradient; backward final RMSNorm и last-layer MLP запускать только на этих rows; scatter-add обратно не нужен до residual, если representation держать sparse до входа последнего attention. Затем один раз densify `dO` перед attention backward. 3–6 ч. Это особенно выгодно, если assistant-label fraction существенно меньше 50%.

**Седьмое — TN/NT physical layout sweep.** Для каждого recurrent GEMM shape собрать четыре варианта на одних и тех же pointers: `A@B`, `A@B.T`, `A.T@B` через view/stride conventions, чтобы cuBLAS видел разные op flags без реальной transpose copy. Измерить 500–1000 повторов при warmed power-capped T4. Публичные T4 measurements показывают сильную shape sensitivity, но не дают вашей exact configuration. citeturn329695search5 Внести только варианты с >2–3% устойчивого выигрыша. 2–4 ч.

**Восьмое — consumer-deadline copy scheduler.** Вместо отдельных логик head/NF4/activation сделать одну маленькую Python очередь `(deadline_layer, direction, bytes, event)`. Копии выдавать в порядке ближайшего consumer; большие head chunks дробить только до точки, где H2D начинает стабильно достигать ~ваших 12 GB/s, обычно стоит проверить 8/16/32/64 MiB. CUDA подтверждает преимущество batching и pinned memory, но exact T4 optimum надо измерить. citeturn798833search2 2–4 ч.

**Девятое — import/load overlap.** Запустить минимальный путь `torch + transformers model classes + safetensors` первым; сразу начать model materialization/quantize; в Python thread импортировать `peft`, затем `trl` и Trainer internals, но не использовать их до join непосредственно перед trainer construction. Это не `sys.modules` stub и не background process. Известный eager-import overhead Transformers 5.16.1 делает эксперимент особенно оправданным. citeturn872934search2 2–4 ч.

**Десятое — double-buffered loader.** Сначала profile 3,2 с: время `mmap/pagefault`, CPU tensor creation, H2D, quantization. Если CPU/file→pinned заметны, использовать два 32–64 MiB pinned slabs, один thread читает следующий contiguous range, GPU stream копирует предыдущий и сразу запускает NF4 quantization. Такой pipeline подтверждён как эффективная weight-loading pattern на других NVIDIA системах. citeturn550677search8turn550677academia9 При вашем небольшом checkpoint ожидал бы несколько десятых секунды, не секунды.

Если первые три пункта дадут середину диапазонов, wall может уйти примерно с 43,4 до **41,5–42,3 с**. Добавление startup work, GEMM alignment/layout и sparse/truncated backward реалистично может снять ещё **1–3 с**. Поэтому без INT8 или Tensor-Core fused NF4 GEMM я вижу более консервативный достижимый диапазон **38–41 с**. До **35–37 с** можно добраться, если post-RoPE storage оказывается ближе к верхней оценке, import/load overlap даст ~0,7–1 с, а M/layout tuning даст несколько процентов от ваших 150–185 мс GEMM. **32–35 с** уже требует одной «большой» оптимизации порядка 50–100 мс/шаг либо нескольких удачных эффектов одновременно.

## Дальнейшая работа

Самый очевидный проект свыше восьми часов — **собственный sm75 NF4×FP16 Tensor-Core GEMM**. Архитектурно он должен копировать AWQ/ExLlama-подход: packed 4-bit load, NF4 LUT + double-quant absmax decode, staging fp16 fragments, `ldmatrix`, затем `mma.sync.m16n8k8`, с раздельными kernels/configs для M≈100–500 и M≈800–2000. AWQ демонстрирует dequant-to-fp16 + shared + MMA паттерн. citeturn630822search1 ExLlama показывает рабочий sm75 `m16n8k8` PTX. citeturn630822search0 bitsandbytes даёт точную NF4 LUT semantics. citeturn706614search0turn706614search1

Но stock Triton 3.6 здесь мешает больше, чем помогает: upstream sm75 MMA pass отключён, а `inline_asm_elementwise` не даёт удобного dot-fragment layout contract. citeturn914405search0turn771363search4 Community `triton-turing` фактически реализует недостающую compiler часть и уже показывает 87–89% cuBLAS FP16 на sm75 Titan RTX, однако это fork/rebuild Triton, что почти наверняка конфликтует с вашим условием «версии пакетов зафиксированы». citeturn914405search5 Если правила разрешают патчить установленный Triton compiler без изменения reported version, это технически наиболее мощное направление, но оценка скорее **1–3 дня**, а не 4–8 часов.

Второй проект >8 ч — полноценный **split attention backward** для Turing с dQ только по active query rows и отдельным dK/dV. На современных Triton он неинтересен без MMA; на CUDA PTX/C++ он может конкурировать с CUTLASS только после серьёзного tiling/pipelining. Я не нашёл опубликованного T4 benchmark для вашей формы 4×100–500, 12Q/2KV, d128, который убедительно превосходил бы PyTorch sm75 efficient-attention backward. PyTorch уже имеет dedicated sm75 kernels. citeturn801057search3 Поэтому это исследовательский проект, не ближайший конкурсный выигрыш.

Третий — глубокий loader rewrite с прямым safetensors range reader и batched NF4 quantization. fastsafetensors показывает, что архитектурно здесь возможны многократные ускорения на больших моделях, но его 4,8–7,5× результаты относятся к 7B–176B моделям и другой инфраструктуре. citeturn550677academia9 На вашем 2,5 GB checkpoint Amdahl быстро упирается в imports, Python startup и trainer construction, поэтому после первых 0,3–0,7 с дальнейшая работа почти наверняка имеет плохую окупаемость.

Наконец, я бы **не инвестировал** время в ещё один Triton attention, deliberate power-throttling tricks, полный resident NF4 или очередной cuBLASLt autotune. На sm75 современные Triton attention kernels лишены Tensor Cores. citeturn755369search0 Power throttling T4 реальный, но NVIDIA не приводит evidence, что искусственное чередование kernel classes повышает sustained throughput. citeturn329695search0turn329695search2 Полный NF4 residency даёт плохой выигрыш на MiB относительно head/QKV retention, а cuBLASLt вы уже практически исчерпали.

Из практик Liger/Unsloth и kernel competitions у вас уже реализована большая часть высокоценного набора: fused linear+loss, RMSNorm, RoPE, SwiGLU, LoRA fast paths, recompute/offload и depadding. Liger публиковал около 20% throughput gain и 40–60% memory reduction, но на A100/FSDP и за счёт именно этих fusion patterns, которые у вас уже присутствуют. citeturn337321search3turn337321search5 GPU MODE и более свежие kernel competitions подтверждают общий инженерный урок: выигрывают hardware-specific tiling, точное сокращение memory traffic и per-shape specialization, а не универсальные «умные» kernels. citeturn197267search1turn197267search3 В вашей конкретной конфигурации оставшийся дешёвый резерв — это прежде всего **использовать 500 MiB свободной памяти для устранения реального wall-time**, затем **математически удалить ненужный backward**, и только после этого браться за sm75 MMA.

## План S1: холодные ядра torch на шаге 0 (п. 5)

Что известно. CUDA 12.2+ на Linux грузит модули лениво, при первом запуске ядра, и документация прямо предупреждает, что эта загрузка попадает в измеряемое окно (ссылка в таблице). ## П11. docs/notes/a2-attn-bwd.md (attention backward через батчевые GEMM: NO-GO)

# A2: the attention backward as batched GEMMs (branch claude/e1-exit-attn)

Recommendation of external review 2 (`docs/briefs/astra-answer-2-2026-10-31.md`, section 2): replace
`aten::_efficient_attention_backward` (fmha_cutlassB sm_75, ~0.8 ms per layer at 4 rows of ~200
tokens on the T4) by cuBLAS batched GEMMs and own Triton kernels for the softmax parts.

## What is in the branch

`solution/attn_bwd.py`, switch `SOUP_SOLUTION_ATTN_BWD=math` (default `sdpa` = the original
backward, nothing changes). Wiring: `solution/unpad.py`, three lines in `_VarlenAttention`
(the forward records the step's `Plan`, the backward asks `attn_bwd.backward` first) and one line in
`patch_qwen2_attention` (warm-up and exit log, math mode only). The forward, the attention recompute
of `fused_proj.py` and `_AttnBlock` (SOUP_SOLUTION_ATTN_ONE_FUNCTION, off by default) are untouched.

Per layer: one gather kernel (q, grad_out, k, v token-major -> head-major padded bins), per chunk of
(bin, kv group) entries and per block of query rows five strided-batched GEMMs (S = QK^T fp32 out via
`bmm(out_dtype=float32)`, dV += P^T dO fp32, dP = dO V^T fp32 out, dQ = dS K, dK += dS^T Q fp32) and
two row kernels (causal softmax over each row's own sequence -> P fp16; dS = scale P (dP - sum P dP)
over P), one scatter kernel back to token-major (dK, dV rounded to half once) with zeros for the
alignment tail. GQA: the six query heads of a kv group are consecutive rows of the head-major buffer,
so dK and dV sum them inside the GEMM (no expansion copies, no group sums). Sequences are packed
into bins of LP rows (`layout`: longest row rounded up to NB blocks of 16-multiples, first fit,
longest first): short rows share one square. Query rows go in NB blocks per bin
(SOUP_SOLUTION_ATTN_BWD_BLOCKS, default 2): block t only meets keys 0 .. (t+1) LP / NB - 1, so the
products skip the causal square's upper right part (NB = 2: 3/4 of the square, NB = 4: 5/8). S and
P live in the free tail of fused_proj's shared dequantization buffer (15.75 MiB behind the q|k|v|o
weights the o_proj and q/k/v backward read), as many entries per chunk as fit.
Filter, decided once per step from the row lengths: at least SOUP_SOLUTION_ATTN_BWD_MIN_TOKENS real
tokens (600), the longest row at most SOUP_SOLUTION_ATTN_BWD_MAX_LEN (256), and `work_ratio` (the
math path's score entries over the fmha's causal ones) at most SOUP_SOLUTION_ATTN_BWD_MAX_RATIO;
anything unexpected or an error -> the original backward.

Own kernels: attn_bwd_gather_kernel, attn_bwd_probs_kernel, attn_bwd_dscores_kernel,
attn_bwd_scatter_kernel (check_rules likeness to the example 0.31 / 0.31 / 0.69 / 0.24).

## Numerics

Not bitwise (the brief allows it). Against an fp32 autograd reference (max |err| / max |ref|), random
fp16 q/k/v/dO, 4 rows (T4, below): the original path 2.9e-4 .. 7.9e-4, the math path (NB = 2) 2.5e-4 ..
6.2e-4 (same order,
slightly better: delta from P and dP in fp32 instead of dO . O with O rounded). Tail rows exactly zero.

Verdict (the brief's rule: stop unless < 0.5 ms per layer at L ~ 208): **no-go, A2 closed.** The best
math variant at 4 x ~200 tokens is 0.78 ms against 0.84; the original is faster on every batch shaped
like the task's data (one long row and shorter ones: 0.45-0.68 ms against 0.70-1.30) and on every even
batch from L = 320 up. The only wins are near-even batches of 4 x 200-256 tokens (-0.06 and -0.22 ms
per layer), which random batches of this data almost never form (2-4 of 64 steps have even a
longest row <= 256 at >= 600 tokens). Why: on the power-limited T4 these strided-batched GEMMs run at
5-7 TFLOPS and cost 0.06-0.08 ms each however small, so five GEMMs per row block plus the four own
launches put a floor of ~0.7 ms under the math path, while the fmha kernel skips the causal half and
all padding (its time follows the sum of L^2 / 2: 0.45 ms at the data's typical batch). Queueing costs
0.6-1.6 ms of CPU per layer against 0.18 (16-44 launches), which would also eat the GPU lag of the
long steps. Nothing here makes the 0.5 ms target reachable without an own tensor-core kernel (review
2, section 2.5: not the plan for today).

`rmsnorm.half_of` instead of `x.to(half)` (fused_proj.py: two lines and the import). The final norm

(round to nearest even of the same fp32 product), and the new kernel keeps rms_norm_rows_fwd's tile

[1, 8] instead of [1, 4] and the sum of squares is added in another order (rstd and y then differ in

fused path gives equal hidden states, loss and every LoRA gradient with the switch on and off).

consumer keeps it, as the cast did) and falls back to the cast when the output changed since the
norm (version check), the dtype or shape differs, or no copy exists; `_MLP` keeps its single padded
copy when there is none. Note: test_recompute's decoder-layer memory test fails when it runs after
any tiny-model test in the same process, on main too (order dependence, not this change).
