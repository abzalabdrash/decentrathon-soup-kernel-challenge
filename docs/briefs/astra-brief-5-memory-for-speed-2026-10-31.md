## Что найдено

Triton 3.6 на T4 опускает `tl.dot` до FMA не потому, что не умеет Turing. В `libtriton.so` есть `callMmaTuringFp16` и `callMmaTuringInt8` (`mma.sync.aligned.m16n8k8.row.col.f32.f16.f16.f32` и `m8n8k16...s32.s8.s8.s32`), `NvidiaMmaEncodingAttr::isTuring` (раскладка `nvidia_mma` версии 2.1). Отключён только проход AccelerateMatmul для cc < 80: строка «Dot op using MMA for compute capability 75 has been deprecated. It falls back to the FMA path» (проверено `strings` по `libtriton.so` из venv WSL с triton 3.6.0).

`solution/mma_gemm.py` `install()` ставит хук `triton.knobs.runtime.add_stages_inspection_hook` (его вызывает `CUDABackend.add_stages`, `triton/backends/nvidia/compiler.py:547`). Для ядер с именем `tc_*` стадия TTGIR идёт через штатный `make_ttgir` с capability 80, затем в тексте `versionMinor = 0` меняется на `1` и `"cuda:80"` на `"cuda:75"`, модуль парсится обратно (`triton.compiler.compiler.parse`). Остальное (LLVM, PTX, `ptxas --gpu-name=sm_75`) штатное. Запуск только с `num_stages=1`: конвейер Ampere выдал бы `cp.async`, которого на sm_75 нет. Прочие ядра прогона компилируются как раньше. Харнесс считает и меряет `tc_*` как обычные запуски `JITFunction.run` (`harness/_train.py:56-76`).

Проверка на T4 (`soup-b3-bench1`): в PTX каждого ядра есть `mma.sync.aligned.m16n8k8` (fp16) или `m8n8k16` (int8), есть `ldmatrix`, нет `cp.async` и нет `fma.rn.f32` в цикле; fp16 против `torch.mm` с ошибкой 0, int8 против `torch._int_mm` без расхождений.

Вопрос организаторам (это не буквально ответ 18, там был inline PTX): `docs/briefs/organizers-question-b3-2026-10-31.md`. До ответа всё за выключенными переключателями.

## Строка для README (если организаторы ответят «да»)

Tensor cores from our own Triton kernels. Triton 3.6 lowers `tl.dot` to FMA code on sm_75 because its layout pass refuses MMA layouts below compute capability 80, although the library still contains the Turing lowering (`mma.sync.aligned.m16n8k8` for fp16, `m8n8k16` for int8). `solution/mma_gemm.py` registers Triton's stage hook (`triton.knobs.runtime.add_stages_inspection_hook`) for our kernels named `tc_*` only: their TTGIR is built with the Ampere layout pass and marked as a Turing (mma 2.1) cuda:75 module; LLVM lowering, PTX and ptxas run unchanged for sm_75, with `num_stages=1` (no `cp.async` on Turing). The kernels compile inside the measured run with empty caches and launch through `JITFunction.run`, so the harness counts and times them. Two of them replace a cuBLASLt int8 GEMM and the pass over its int32 result: the MLP's int8 gate|up forward with its SwiGLU epilogue, and the backward's int8 `W_down^T g` product with the SwiGLU derivative. Integer accumulation is exact and the epilogues repeat the same fp32 operations, so their outputs are bit-for-bit those of the two-kernel paths; the int32 buffers (up to 70 MiB at 2,048 tokens) are never allocated.

## Ответы организаторов на наши четыре вопроса (30 октября, вечер)

1. Процесс-помощник для компиляции Triton: **нельзя**, это фоновый процесс (запрет из раздела «обход замера»); компилировать в потоке того же процесса или синхронно; пустой кэш и учёт времени запрет не снимают. Действие: прогрев возвращается в поток внутри процесса, код помощника убрать до сдачи.
2. Эмбеддинг и lm_head в pinned-памяти хоста со стримингом головы каждый шаг: **можно** как собственный CPU-оффлоад; копии и синхронизация в замере, значения, dtype и обязательные выходы сохраняются.
3. Хвост выравнивания до кратного 16: **можно** как внутреннее выравнивание вычислений; фиктивные позиции не должны влиять на реальные токены, attention, loss, метрики, rewind и учитываемое число токенов (тест на это добавляет T12).
4. `TORCHDYNAMO_DISABLE=1` на время импорта bitsandbytes: **можно**, если флаг действует только во время этого импорта, восстанавливается и не меняет путь обучения, харнесс и проверки.

## Чем решение отличается от шаблонного

Varlen-attention одним вызовом на слой с хвостом выравнивания (без цикла по строкам и без repeat_kv), голова за один проход по словарю с онлайн-перемасштабированием накопителя градиента (матрица головы читается один раз за шаг, никогда не резидентна на GPU), кольцо из двух слоёв NF4-весов, стримимых с хоста, оффлоад gate|up на событиях без record_stream, восстановление входов норм в backward своим ядром вместо хранения, компиляция ядер вне главного потока, диагностика пика по снимку аллокатора.

## Схема

Переключатель `SOUP_SOLUTION_INT8_FWD`: как у int8_bwd с main bc18d4b, по умолчанию включён в любом процессе (правило README: одинаковое поведение при замере и в тестах), `=0` выключает; `solution/conftest.py` выключает его в начале каждого теста `solution/` (побитовые тесты fp16-пути), `test_int8_fwd.py` включает явно. Ядра компилирует поток, который стартует на `COMPILE_CALLS = 57`-м подходящем forward MLP (шаг 2); первые `START_CALLS = 224` подходящих forward (8 шагов × 28 слоёв) идут fp16, 225-й ждёт поток, если он не закончил: точка переключения не зависит от таймингов (выбор расписания: ABBA 4–5 ниже). Считаются только forward с включённым autograd (обучение), no-grad forward (rewind Soup) всегда fp16. Путь берётся только когда MLP хранит (gate|up) для backward (не режим recompute) и веса в раскладке nf4.py.

Режим `SOUP_SOLUTION_INT8_FWD_MODE`:
- **`gu` (по умолчанию)**: int8 только для gate|up. (1) `quant_rows_kernel`: x (M, D) fp32 → int8 по токенам (absmax/127; строки паддинга нули); (2) `nf4_int8_gu_kernel`: W_gate и W_up из NF4 сразу в int8 (2I, D) в естественной раскладке с масштабом на выходную строку, одна программа читает коды absmax своих строк (максимум строки = максимальный absmax её блоков: у каждого блока NF4 есть код ±1), потом распаковывает; без вспомогательных тензоров между шагами; (3) `torch._int_mm(W_q, x_q.t())` → int32 (2I, M), «TN»; (4) `int8_gate_up_kernel`: gate, up = acc · s_w[строка] · s_x[токен] в fp32 → half в (gate|up) (тензор для backward и оффлоада, контракт P1 не тронут) и сразу SwiGLU в half (I, M) для down; (5) down остаётся fp16 GEMM fused_proj на этом выходе.
- `all`: ещё и down в int8 (квантование SwiGLU-выхода по токенам с максимумами по группам признаков из эпилога, транспонирующее квантование `int8_hidden_kernel`, распаковка W_down в int8, `_int_mm`, эпилог `int8_out_kernel`). Численно непригоден (ниже).

int8-веса лежат в общем буфере распаковки fused_proj (int8 gate|up ровно размера одного fp16-веса (I, D)); слоты кольца весов берутся `acquire`/`release` вокруг распаковки. int32-произведение (2I, M) временное, 72 КБ на токен: с ним forward MLP стал пиком прогона (ABBA1: 395 → 475 MiB), поэтому `SOUP_SOLUTION_INT8_FWD_CHUNKS=5` (по умолчанию) делит его на 5 произведений по 2I/5 строк в одном переиспользуемом буфере (14 КБ на токен; строки int8-весов чередуются по кускам: gate куска k, up куска k).

**Разложение top-k каналов** (`SOUP_SOLUTION_INT8_FWD_TOPK=16`, по умолчанию; 0 выключает), как в LLM.int8: 16 входных каналов слоя с наибольшим max |x| идут мимо int8-произведения и добавляются в fp32. Набор каналов фиксируется на весь прогон: fp16-forward до переключения (шаги 0–7) копят max |x| по каналам на модуле (`observe`: один `vector_norm(inf)` и `maximum`, только GPU, без синхронизаций), первый int8-forward слоя берёт `topk` (`channels`). Правила: уточнение к ответу 11 (main 9317a4d, `docs/briefs/organizers-questions-2-2026-10-31.md`): выбор каналов внутри прогона по первым fp16-шагам с фиксированным дальше набором разрешён (вариант (а); у нас 8 шагов вместо 4). `quant_rows_kernel` выносит эти каналы в x_k (M, 16) fp32 и не учитывает их в масштабе токена; дополнительные программы того же запуска распаковки (`_topk_cols`) пишут fp32-столбцы W_gate и W_up (2I, 16); эпилог добавляет `tl.dot(W_k, x_kᵀ)` до округления в half.

**Ожидание копии**: при раннем оффлоаде fp16-путь ждёт D2H-копию (gate|up) предыдущего слоя (`offload.drain_inflight`) до начала MLP; int8-путь ждёт её прямо перед выделением своего (gate|up), после квантования x, распаковки весов и первого int8-произведения (`before_alloc`), так что копия летит под ними. Пик не растёт: в этот момент живы предыдущий (gate|up) и один кусок int32.

Список fp16-слоёв: `SOUP_SOLUTION_INT8_FWD_FP16_LAYERS` (`0-4`, `1.2.4`, `2,26`; индекс decoder-слоя; MLP без метки считается из списка), по умолчанию пусто.

## Итог и риски

- Выигрыш стены в одной сессии ABBA: −0,63 с (ABBA 5, умолчания 7313c94), то есть ниже критерия влития −1 с. Шаги после переключения −13…−18 мс на шаг (микробенч обещал −23…−37); причины: forward частично упирается в D2H-копию (gate|up) предыдущего слоя (ожидание копии уже перенесено, см. «Схема»), куски int32 (~6 мс на шаг) и top-16 (~3–8 мс на шаг), компиляция трёх ядер (~0,25 с на шагах 2–3).
- Память: +20 MiB (395 → 415) от куска int32 в момент forward MLP, который и так пик прогона. На строках жюри seed 127 тоже 415.
- Численность: кривые 0,10–0,15 % (проверка 6 до 3 %), entropy и accuracy 0,2 / 0,6 % (проверка 5 до 3 %), eval −0,04…+0,006 %. Первые 8 шагов идут fp16, первый шаг не меняется.
- Что может дать ещё: (1) лаунчеры int8-ядер (обоих направлений) собирать заранее в потоке `SOUP_SOLUTION_LAUNCHERS_EARLY` (добавить `int8_fwd._warm` и `int8_bwd._warm` в `warmup._probe_registrations`, зона L1): минус сборка gcc на шагах 2–3; (2) разгрузка PCIe forward (P1): при снятом ограничении копией выигрыш шагов растёт к микробенчу; (3) эпилог мог бы писать (gate|up) сразу в mapped pinned-память хоста (без D2H-копии и без 36 КБ/токен на GPU) — это контракт оффлоада P1.
- Переключатели: `SOUP_SOLUTION_INT8_FWD` (0/1), `_MODE` (gu/all), `_TOPK` (16; 0, 32, 64), `_CHUNKS` (5; делители 40), `_START_CALLS` (224), `_COMPILE_CALLS` (57), `_FP16_LAYERS` (пусто), `SOUP_SOLUTION_INT8_COMPILE` (first/apply).

## Совместная ветка с P1 (d26e4fc)

Влиты main 9317a4d (int8 включается в любом процессе, conftest) и `claude/p1-offload-int8-8429f6` 04d6ada (gate|up уходит на хост в int8: int16 на пару (gate, up) поверх gate-половины и fp32-масштабы на токен и группу из 128 признаков). Мой int8-путь пишет эту форму сам прямо из int32-эпилога: `offload.reserve_int8(gate_up)` (решение offload_early без копии: eligible + applies + бронь слота хоста) перед первым эпилогом, эпилог с `WIRE` (тайл = GROUP признаков × 32 токена) пишет int16-форму и масштабы из тех же half-значений вместо самих half-значений, затем `offload_early(gate_up, wire=(q, s))`; если бронь не дана, эпилог пишет half, а `offload_early(gate_up, decided=True)` запускает half-копию без второго вызова applies. fp16-путь остаётся путём P1 (`swiglu_quant`). Тесты: форма побитово равна `offload_int8.encode` того же half (gate|up); на трёх MLP с оффлоадом ошибка градиента против half-оффлоада та же, что у fp16-пути P1 (0,96 % / 3,86 % при fp16 / int8 backward), forward побитово тот же; локально 141 тест прошли.
