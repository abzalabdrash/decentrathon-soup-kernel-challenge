1. Однопоточный backward: `with torch.autograd.set_multithreading_enabled(False): loss.backward()` — публичный API PyTorch, действует только на время вызова backward: узлы autograd выполняются на вызывающем потоке, а не на отдельном потоке устройства. Ядра, их порядок и результат те же; экономия одной рабочей области cuBLAS (−30 MiB). Это не настройка интерпретатора вроде `gc`/`setswitchinterval` из ответа 31. Можно?

2. Освобождение pinned-памяти хоста в конце обучения: после последнего шага обычный (не daemon) поток освобождает наши pinned-буферы оффлоада (`cudaFreeHost`, `cudaHostUnregister`) параллельно с сохранением адаптера Soup. Процесс завершается штатно (atexit, финализаторы, без `os._exit`), все выходы Soup сохраняются. Иначе ядро ОС ~0,8 с разбирает 3,6 ГБ закреплённой памяти уже после выхода. Можно?

3. C-лаунчеры Triton: Triton собирает для каждого ядра маленькую C-заглушку запуска системным компилятором с `-O3`; мы в `apply()` собираем её с `-O0` (тот же исходник, флаги и библиотеки). Сами ядра (TTIR → PTX → cubin) Triton компилирует полностью и без изменений, кэш пустой. Это сокращает компиляцию, на время запуска ядер не влияет. Можно?
