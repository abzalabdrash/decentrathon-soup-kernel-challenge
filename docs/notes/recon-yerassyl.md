## 1. Замкнутый бюджет стены

Стена харнесса идет от `perf_counter()` до возврата `proc.wait()` (`harness/common.py:107-115`). Метки `[solution] phase` отсчитаны от `psutil.Process().create_time()`, а psutil берет время загрузки ОС целыми секундами (`btime`), поэтому у всех меток одной сессии общий сдвиг 0..1 с. Разности между метками точные, граница «пролог / после exit» плавает, поэтому эти две части ниже даны суммой. Пример: в m6-full метка exit +43,54 при стене 43,37.

Текущий код по поведению (вариант base в `soup-b4-early2`, full и jury той же сессии второго фронта; до влития раннего освобождения P2), секунды:

|---|---|---|---|

| apply | 3,42 / 3,43 / 3,13 | 3,21 / 3,22 | наша (импорты, которые Soup иначе сделал бы позже, и патчи) |

## 2. Карта трат CPU и GPU

Старт (startup.md, разделы 2, 3а, 3б). Критический путь целиком главный поток: apply, CLI, загрузка, сборка. Прогрев Triton (16 вариантов, 5,05 с на двух воркерах) кончается за 2,2..2,7 с до `train begin`, то есть не на критическом пути, но мешает через GIL: компиляция Triton 3.6 держит GIL около 35 % своей стены (фронтенд на Python и ~60 % `make_llir`, замер в WSL, `startup.md` 3а), и без прогрева загрузка шла 2,0 против 3,3 с (L1). Главный поток ждет staging pinned-цикла 0,52..0,74 с за загрузку. Еще 7 int8-вариантов компилируются на шагах 1-5 (2,5..2,7 с потоко-времени).

CPU шага (cpu.md). Верхняя граница того, что CPU держит GPU внутри шагов: до 0,53 с на публичных (forward 11 коротких шагов < 600 токенов), 0,15..0,35 с у жюри; плюс начало шага 0,12 с; зазор между шагами (две синхронизации харнесса) 0,37..0,41 с публично и 0,47..0,48 с у жюри, внутри него в основном коммит трекера SQLite 2,7..4,3 мс на шаг. Шаги от 600 токенов упираются в GPU. Простой «CPU не поставил ядро» 97 мс/шаг из трассы P2 нельзя умножать на 64: это 4 трассированных шага, и трассировка замедляет CPU. CUDA graphs: потолок на текущем коде ниже оценки G1 (0,2..0,3 с) при +82 MiB, NO-GO остается.

GPU шага (gpu.md, P2). На жюри-строках шаг упирается в GPU: простой ~35 мс из 504..594 мс, ожидания копий не больше 7 мс на шаг. Крупнейший клей torch: ~820 запусков и ~10 мс GPU на шаг в int8-backward MLP (`int8_bwd.py:193-199`, `:337-344`), его слили две ветки независимо (`claude/b5-fused-quant`, `claude/h2-glue`). Сверх них в attention 4..6 мс на шаг (развертка k/v три раза за слой, клон v, копия grad_v, каст x16). Шина после раннего освобождения P2 больше не главный рычаг: весь NF4 на GPU дает -0,65 с при 1 025 MiB (STATUS main 20:40).

Хвост (tail.md). После метки exit около 0,8 с (прямой замер E1), на уровне базы. Внутри хвоста в train сохранение `checkpoint-64` около 0,51 с (выходные файлы, не трогаем) и +0,43 с от потока освобождения pinned, который стартует на `on_step_end` 64-го шага ровно под копии чекпойнта.

## 4. Что уже делают подчаты и где пересечения

L2: спекулятивная NF4-загрузка, `do_not_specialize`, nice потока компиляции. Новое для L2 из разведки: прогрев уже не на критическом пути, поэтому nice и меньше воркеров теперь могут выиграть (S1 отверг их при нулевом запасе); `do_not_specialize` не сокращает 7 компиляций вне прогрева (они различаются constexpr); перенос int8-компиляций в прогрев снова имеет смысл.
I1 и P1 (int8): компиляция на шагах 1-5 и варианты для окна до переключений (строка таблицы выше).
H1/H2 и второй фронт (b5): один и тот же клей int8-backward, вливать одну ветку.
P2: раннее освобождение влито; на жюри-строках копии дают не больше 7 мс на шаг, дальше шина не главный рычаг.

## 5. Сумма и цель

Сумма оценок раздела 3 с перекрытием рычагов старта (они делят один GIL и один критический путь): от -1,3 до -3,9 с к 43,9 с main 55f4e3e, то есть 40..42,5 с на публичных строках. Ресерч (`docs/notes/recon/research.md`, `score.py`): при 395 MiB равенство с заявкой соперника (37,8 с при базе 83,7, 574 MiB) наступает на 40,1 с публично, 1 с стены стоит 1,02 балла, это 54 MiB пика; реалистично 42-42,5 с, 40,1 с с вероятностью около 10 %. 37-39 с измеренного пути нет.

Уточнения по прогонам разведки 31.10 вечером (код main 71074d8, `soup-recon-pub`, `soup-recon-jury`): от `apply begin` до первого шага 11,75 с, CPU главного потока 8,85 с, ожидание staging 0,70 с, ожидание GIL ~2,2 с; GIL занят ~10-10,5 из 11,75 с (startup.md, раздел 6). Последняя регистрация прогрева `fused_proj_nf4_dequant4` (1,80 с) ложится на dill-хеш, то есть на критический путь. CPU держит GPU 1,8-2,2 с за прогон на публичных строках (верхняя граница по трассе, cpu.md); реально убираемо 0,3-0,5 с. Пересчет attention 20,9 мс/шаг публично, 34,4 мс на длинном шаге; без памяти из него уходит ~2,6 мс (gpu.md). На строках жюри 42000/51800 (seed 157) plain 47,14 с, пик 453 MiB.
