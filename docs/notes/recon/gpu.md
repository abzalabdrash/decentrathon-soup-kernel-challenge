## 3. Что держит шаг на строках жюри

[P2]: шаги 504–594 мс, простой ~35 мс, значит ~470–560 мс работы GPU на шаг; на публичных 288–440 мс при простое ~129. С длиной растут GEMM, attention (квадратично по строке), активационные H2D/D2H (оффлоад), RMSNorm, клей ∝ N. NF4 (1,3 ГБ H2D на шаг) и голова от N не зависят. Потолки на жюри-строках (оценка, не проверено на T4):

- ожидания копий: ≤7 мс на шаг ([P2]: 3,1 + 2,8 + 0,8), ≤0,45 с за прогон; early release там нейтрален (soup-p2-abba-er-jury, [P2] раздел 3);
- клей int8 backward (b5/h2): ~10 мс × N/830 на шаг GPU, на жюри ~12 мс, ≤0,75 с за прогон по GPU; ABBA b4-early2 на публичных дала −0,42 с на шагах 8+;
- остаток клея attention (раздел 4): 4–6 мс на шаг, ≤0,35 с;
- GEMM fp16: крупнейшая статья, сокращается только int8 (I1 forward: −13…−18 мс на шаг после переключения в ABBA 5, но −0,63 с стены и пик 395 → 475 без кусков; выключен по умолчанию, `docs/notes/i1-int8-fwd.md:7`, `:132`).

## 4. Сравнение с базой (GPU): что мы повторяем без нужды

База (bnb `MatMul4Bit` + peft LoRA, без нашего патча) распаковывает каждый NF4-вес в каждом forward и backward отдельно (7 + 7 на слой), держит активации на GPU и не пересчитывает attention. Наше: распаковка q|k|v|o одним запуском (`nf4_dequant4_kernel`, ~2 на слой: forward и пересчёт), gate/up/down по кольцу (`nf4_dequant_kernel`, 3 на слой) и int8-декод в backward (`nf4_int8_t_kernel`, 3 на слой), то есть повторов распаковки сверх необходимого для стриминга нет. Повторы, которые остались:
