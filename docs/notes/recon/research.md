## 1. os._exit

Полный разбор: scratchpad `exit_report.md` (субагент). Исходники Soup/torch/logging из WSL `~/soupenv/lib/python3.13/site-packages/`.

Что идёт после записи metrics.json. Харнесс ловит `SystemExit` от `soup_cli.cli.run` и берёт код (`harness/_train.py:174-179`; Soup сам превращает любое исключение в `sys.exit(1)`, `soup_cli/cli.py:1032-1059`), затем `own_ms()` (~41 тыс. `elapsed_time`, `_train.py:79-83`), `write_json(metrics)` через `with open` (`_train.py:217`, `common.py:159-162`) и `sys.exit(code)` (`_train.py:218`). Потом финализация модулей с полной сборкой, C-выход (статические деструкторы, CUDA runtime), разбор процесса ядром, и только тогда возвращается `proc.wait()` (`harness/common.py:111-115`).

Прямой замер E1 на T4 с `EXIT_RELEASE=1` (`e1-exit-head.md:63-70`): atexit 0,07, финализация 0,12, C-выход 0,25, ядро 0,36 с; без освобождения pinned ядро 0,88 с (`e1-exit-head.md:69`).

Почему нельзя просто `os._exit(0)` в atexit (опыт субагента, WSL, Python 3.13): внутри atexit код `SystemExit` не виден (`sys.last_exc`, `sys.last_value`, `sys.exc_info()` пусты после `sys.exit(3)` и `raise SystemExit(5)`), значит упавший Soup или упавший pytest (`python -m pytest` завершается `raise SystemExit(код)`) вернули бы 0. Это скрытие ошибки, прямо запрещено ответом (1).

Дизайн, совместимый с ответом (1), за переключателем `SOUP_SOLUTION_EXIT_FAST`, ставится в начале `apply()`:

```python
_OUT = {"code": None}

def install():
    import atexit, soup_cli.cli as cli
    original = cli.run                     # точка входа `soup = soup_cli.cli:run` (entry_points Soup 0.77.0)
    def run(*a, **kw):
        try:
            r = original(*a, **kw)
        except SystemExit as e:            # та же нормализация, что soup_cli/cli.py:1035-1041
            c = e.code
            _OUT["code"] = 0 if c is None else (c if type(c) is int else 1)
            raise
        except BaseException:
            _OUT["code"] = "error"; raise
        _OUT["code"] = 0
        return r
    cli.run = run                          # харнесс импортирует run после apply (_train.py:175)
    atexit.register(_final)                # первый из наших: выполнится после всех наших колбэков

def _final():
    code = _OUT["code"]
    if type(code) is not int or getattr(sys, "last_value", None) is not None:
        return                             # run() не вызывался (pytest) или была ошибка: обычный выход
    import torch, logging
    if torch.cuda.is_initialized():
        torch.cuda.synchronize()
    logging.shutdown()                     # его колбэк ниже нашего в стеке, вызываем сами
    sys.stdout.flush(); sys.stderr.flush()
    os._exit(code)
```

Как это закрывает условия ответа (1): к моменту `_final` все не-демон потоки уже присоединены (`threading._shutdown` идёт до atexit) и все наши колбэки отработали, включая join потоков компиляции и дозапись трекера; `synchronize` внутри замера; код выхода тот же, что у харнесса, взят у Soup, без чтения metrics.json и без определения харнесса; `rewind.jsonl` открывается заново на каждую запись (`soup_cli/monitoring/rewind_log.py:93,171`), stdout без буфера (`PYTHONUNBUFFERED=1`, `harness/common.py:41`), `logging.shutdown` вызывается явно. Пропускаются только финализаторы weakref (уборка в памяти) и флаг DataLoader. В `tests/` `soup_cli.cli.run` никто не вызывает (grep `soup_cli.cli import`, `CliRunner` пуст), поэтому в pytest `_final` ничего не делает и итоговая строка и код pytest не меняются.

Открытые места: (а) SQLite трекера: явного `tracker.close()` в `soup_cli/commands/train.py` нет, коммиты уже в WAL, рядом с базой останется `-wal` (не проверено; харнесс `experiments.db` не читает, `harness/run_task.py:75-93`); (б) проверка 9 требует `gpu_start_mib` ≤ 1000 у следующего прогона (`harness/check_rules.py:419-438`): освобождает ли драйвер память GPU к возврату `wait()` после `os._exit`, на T4 не проверено, это первое, что смотреть; (в) различие «в pytest обычный выход, в `soup train` быстрый» возникает не из обнаружения, а из того, вызывался ли `soup_cli.cli.run`; формально это одно правило, но я бы задал организаторам короткий вопрос: «обёртка точки входа Soup ради кода выхода, затем `os._exit(code)` после всех atexit наших модулей, synchronize и logging.shutdown: допустимо?».
