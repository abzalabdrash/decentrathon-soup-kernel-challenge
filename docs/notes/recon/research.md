## 1. os._exit

Полный разбор: scratchpad `exit_report.md` (субагент). Исходники Soup/torch/logging из WSL `~/soupenv/lib/python3.13/site-packages/`.

Что идёт после записи metrics.json. Харнесс ловит `SystemExit` от `soup_cli.cli.run` и берёт код (`harness/_train.py:174-179`; Soup сам превращает любое исключение в `sys.exit(1)`, `soup_cli/cli.py:1032-1059`), затем `own_ms()` (~41 тыс. `elapsed_time`, `_train.py:79-83`), `write_json(metrics)` через `with open` (`_train.py:217`, `common.py:159-162`) и `sys.exit(code)` (`_train.py:218`). Дальше по порядку: `threading._shutdown` (сначала `_threading_atexits` LIFO, потом join не-демон потоков, в том числе `soup-exit-release`, `exit_release.py:70`); atexit LIFO, где наши колбэки (зарегистрированы в `apply()` и позже) идут первыми: `phases.py:70`, `exit_release.py:73`, `weight_stream.py:960`, `head_stream.py:832/891`, join потоков компиляции (`int8_fwd.py:395`, `int8_bwd.py:248`, `offload_int8.py:232`), `offload.py:211`, `warmup.py:573/842`, `launcher_one.py:282`, `tracker_async.py:162`; последними идут колбэки, зарегистрированные до `apply()`: `logging.shutdown` (импорт logging внутри `import torch`), `weakref.finalize._exitfunc` (~30 мс финализаторов torch, `docs/notes/e1-exit-head.md:76-77`), флаг DataLoader torch. Потом финализация модулей с полной сборкой, C-выход (статические деструкторы, CUDA runtime), разбор процесса ядром, и только тогда возвращается `proc.wait()` (`harness/common.py:111-115`).

Прямой замер E1 на T4 с `EXIT_RELEASE=1` (`e1-exit-head.md:63-70`): atexit 0,07, финализация 0,12, C-выход 0,25, ядро 0,36 с; без освобождения pinned ядро 0,88 с (`e1-exit-head.md:69`).

Почему нельзя просто `os._exit(0)` в atexit (опыт субагента, WSL, Python 3.13): внутри atexit код `SystemExit` не виден (`sys.last_exc`, `sys.last_value`, `sys.exc_info()` пусты после `sys.exit(3)` и `raise SystemExit(5)`), значит упавший Soup или упавший pytest (`python -m pytest` завершается `raise SystemExit(код)`) вернули бы 0. Это скрытие ошибки, прямо запрещено ответом (1).

Дизайн, совместимый с ответом (1), за переключателем `SOUP_SOLUTION_EXIT_FAST`, ставится в начале `apply()`:

```python
_OUT = {"code": None}

def install():
    import atexit, soup_cli.cli as cli
    original = cli.run                     # точка входа `soup = soup_cli.cli:run` (entry_points Soup 0.77.0)
    def run(*a, **kw):
        try:
            r = original(*a, **kw)
        except SystemExit as e:            # та же нормализация, что soup_cli/cli.py:1035-1041
            c = e.code
            _OUT["code"] = 0 if c is None else (c if type(c) is int else 1)
            raise
        except BaseException:
            _OUT["code"] = "error"; raise
        _OUT["code"] = 0
        return r
    cli.run = run                          # харнесс импортирует run после apply (_train.py:175)
    atexit.register(_final)                # первый из наших: выполнится после всех наших колбэков

def _final():
    code = _OUT["code"]
    if type(code) is not int or getattr(sys, "last_value", None) is not None:
        return                             # run() не вызывался (pytest) или была ошибка: обычный выход
    import torch, logging
    if torch.cuda.is_initialized():
        torch.cuda.synchronize()
    logging.shutdown()                     # его колбэк ниже нашего в стеке, вызываем сами
    sys.stdout.flush(); sys.stderr.flush()
    os._exit(code)
```

Как это закрывает условия ответа (1): к моменту `_final` все не-демон потоки уже присоединены (`threading._shutdown` идёт до atexit) и все наши колбэки отработали, включая join потоков компиляции и дозапись трекера; `synchronize` внутри замера; код выхода тот же, что у харнесса, взят у Soup, без чтения metrics.json и без определения харнесса; `rewind.jsonl` открывается заново на каждую запись (`soup_cli/monitoring/rewind_log.py:93,171`), stdout без буфера (`PYTHONUNBUFFERED=1`, `harness/common.py:41`), `logging.shutdown` вызывается явно. Пропускаются только финализаторы weakref (уборка в памяти) и флаг DataLoader. В `tests/` `soup_cli.cli.run` никто не вызывает (grep `soup_cli.cli import`, `CliRunner` пуст), поэтому в pytest `_final` ничего не делает и итоговая строка и код pytest не меняются.

Открытые места: (а) SQLite трекера: явного `tracker.close()` в `soup_cli/commands/train.py` нет, коммиты уже в WAL, рядом с базой останется `-wal` (не проверено; харнесс `experiments.db` не читает, `harness/run_task.py:75-93`); (б) проверка 9 требует `gpu_start_mib` ≤ 1000 у следующего прогона (`harness/check_rules.py:419-438`): освобождает ли драйвер память GPU к возврату `wait()` после `os._exit`, на T4 не проверено, это первое, что смотреть; (в) различие «в pytest обычный выход, в `soup train` быстрый» возникает не из обнаружения, а из того, вызывался ли `soup_cli.cli.run`; формально это одно правило, но я бы задал организаторам короткий вопрос: «обёртка точки входа Soup ради кода выхода, затем `os._exit(code)` после всех atexit наших модулей, synchronize и logging.shutdown: допустимо?».

## 6. Вопрос организаторам про os._exit (текст для чата)

> По вашему ответу про `os._exit` уточняем конкретную схему. В `apply()` мы оборачиваем точку входа Soup `soup_cli.cli.run`, чтобы запомнить её код выхода (из `SystemExit` Soup, с той же нормализацией, что делает сам Soup), и регистрируем колбэк atexit. Он выполняется после всех atexit наших модулей: присоединены потоки компиляции и освобождения pinned-памяти, дописаны записи трекера SQLite (все закоммичены, явного `close` нет и в самом Soup). Затем колбэк делает `torch.cuda.synchronize()`, `logging.shutdown()`, сброс stdout/stderr и вызывает `os._exit` с тем же кодом. Если `run()` не вызывался (pytest) или было необработанное исключение, колбэк ничего не делает, выход обычный. `metrics.json` не читаем, харнесс не определяем. Пропускаются только финализация модулей Python и деструкторы уровня C (CUDA runtime). Допустимо?

## 7. OFFLOAD_ATTN на текущем коде

Что делает. `SOUP_SOLUTION_OFFLOAD_ATTN=1` (`solution/offload.py:114-117`) только помечает тензоры для оффлоада: в `unpad.py:236-243` q, компактные k и v, выход и lse, в `rmsnorm.py:369-372` половинную ветку пост-attention нормы (split sum). Метка ставится, только если `recompute is None` (unpad) и `addends is KEEP_BRANCH` (rmsnorm). По умолчанию `SOUP_SOLUTION_RECOMPUTE_ATTN=1` (`solution/fused_proj.py:1137-1140`, режим `all`): объект пересчёта передаётся в каждый слой, и путь оффлоада не срабатывает. Значит, `OFFLOAD_ATTN=1` без `RECOMPUTE_ATTN=0` ничего не меняет (вариант совпадёт с base); тест `solution/test_xoffload.py:82-103` тоже ставит `recompute=None` явно. Правильный вариант для замера: `SOUP_SOLUTION_OFFLOAD_ATTN=1 SOUP_SOLUTION_RECOMPUTE_ATTN=0` (оркестратору отправлено отдельным сообщением в 21:31).

Что меняется в шаге. Уходит пересчёт в backward: GEMM qkv + addmm LoRA ~13,8 мс, GEMM ветки o_proj ~7,8, fmha forward 7,1, развёртки и RoPE ~5 мс, всего 34-36 мс на длинном шаге (трасса b1, `gpu.md` раздел 3); I1 оценивал на строках жюри до 40 мс/шаг. Взамен на шину идёт 10 КБ/токен/слой в каждую сторону (7 КБ attention + 3 КБ ветка, `fused_proj.py:24-27`): при 830 токенах ~232 МБ, при 1 427 ~400 МБ за шаг в каждую сторону, ~20 и ~35 мс на движок копирования при 11,6 ГБ/с (P2). Копии идут на стороне потока оффлоада и перекрываются с вычислениями, если шина не занята.

Почему ночью было +18 мс/шаг (STATUS main строки 100, 181, 269): (1) окно префетча оффлоадера копировало обратно уже прочитанные дескрипторы, 4-7 КБ/токен/слой лишнего H2D, исправлено в 958d727 после замера; (2) замер был на публичных строках до P1 (gate|up уходил на хост в fp16, вдвое больше байт, чем сейчас с int8-оффлоадом) и до раннего освобождения слотов P2, когда шина была главным ограничением. Почему теперь может быть иначе: на строках жюри шаг упирается в GPU, ожидания копий там ≤ 7 мс/шаг (P2), то есть шина имеет запас, а пересчёт стоит 34-40 мс GPU. Оценка нетто на жюри −15…−30 мс/шаг (−1…−1,9 с за прогон), на публичных ноль или убыток (короткие шаги упираются в CPU forward и в шину головы). Не проверено.

Память. Ночью N1c дал 563 MiB против 541 у N1b с префетчем головы (STATUS main строка 100), то есть около +22 MiB, но на другом коде. Механизм роста: в forward тензоры attention слоя живут на GPU до конца своей D2H-копии (окно оффлоадера `max_inflight` = тензоры слоя + 1 + 6 при ATTN, `offload.py:338`), и это совпадает по времени с forward MLP, который сейчас задаёт пик шага (`solution/head_stream.py` около строки 92, комментарий к `DEFAULT_PREFETCH`, по `loop_report.md`). При 1 427 токенах один слой attention это ~14 МБ, то есть возможна ступень +20 MiB (с 435 до 455) на строках жюри. Это главный риск, смотреть пик nvidia-smi в jabba.

Риски для проверок. Численность: оффлоад отдаёт backward ровно те тензоры, что посчитал forward, пересчёт тоже побитовый, так что проверки 5-7 не задеты. Pytest (проверка 10): если включать по умолчанию, оба переключателя меняются во всех процессах; побитовые тесты пересчёта (`test_recompute`) сами ставят свой режим через `_set(modes, recompute=...)` (так в `test_xoffload.py`), но тесты, полагающиеся на умолчание `RECOMPUTE_ATTN=1`, не проверял. Время: при включении по умолчанию проиграем на публичных строках, если правило не зависит от длины шага; режим `auto` (`fused_proj.py:1164-1180`) делит слои наоборот (пересчёт на длинных шагах, хранение на коротких), под «оффлоад на длинных, пересчёт на коротких» нужен новый код. Моё мнение: сегодня только замер на строках жюри; включать, если jabba покажет ≥ 0,5 с на жюри при пике ≤ 435 и не хуже base на публичных.
