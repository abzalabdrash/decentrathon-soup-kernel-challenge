Простой вычислительного потока, когда CPU ещё не поставил следующее ядро (трасса `soup-recon-pub`, раздел 0), плюс зазор между шагами. Это верхняя граница выигрыша при нулевом CPU, не прогноз.

|---|---|---|
| короткие шаги (< 600 токенов): forward + backward | ~0,86 с (11 x 78 мс; один трассированный шаг 432 токена: 51,7 + 26,3 мс) | ~0,25-0,55 с (3-7 коротких шагов, C1 раздел 7; не проверено) |
| шаги 600-900: forward (backward 0) | ~0,59 с (32 x 18,4 мс; три шага 624-736 токенов: 14,4 / 19,3 / 21,6) | основная масса шагов; P2 на строках seed 157: 21,3 мс/шаг, то есть ~1,1-1,3 с за прогон (P2, трасса main 218c174; не проверено на recon-jury) |
| шаги от 900 | не трассированы; по таймлайну меньше, чем 600-900, оценка до 0,35 с (не проверено) | входят в строку выше |
| зазор между шагами (GPU пуст, синхронизация харнесса) | 0,36-0,39 с (recon-pub plain/cpuprof/timing; B4 0,36-0,38) | 0,47-0,48 с (b4-jury, строки 31000) |
| итого | **~1,8-2,2 с** | **~1,6-2,0 с** (не проверено) |

Поправки: трасса замедляет CPU примерно на 10 % (шаги 9-11: 374 / 340 / 302 мс под трассой против 343 / 303 / 277 мс в `plain`), поэтому числа трассы скорее завышены; сессия recon-pub медленная (plain 47,78 с) и это код main 71074d8 без раннего освобождения P2. Моя первая оценка по таймлайну B5 (до 0,75 с внутри шагов) была занижена: в шагах 600-900 lag на границах слоёв в первых 10-13 слоях всего 1-3 мс, и внутри слоя GPU успевает опустеть; трасса это видит, таймлайн по границам слоёв нет.

Что из этого реально убирается по правилам: трекер в потоке (`SOUP_SOLUTION_TRACKER_THREAD=1`, разрешён ответом 16 волны 2; 0,28 с потолок, L1 мерил -0,13 с); CPU forward в начале каждого шага и в первых слоях (главная часть 0,59 с в шагах 600-900); CPU обоих проходов коротких шагов. Моё мнение: реально срезать 20-30 % CPU forward значит 0,3-0,5 с на публичных строках и примерно столько же на жюри, плюс 0,13 с трекера. Цель 37 с этим не берётся, но это самый крупный оставшийся CPU-рычаг, и сидит он в forward, а не в backward (ABBA b5-fq, раздел 5).

Обёртка харнесса на каждый наш Triton-запуск (`harness/_train.py:60-79`): подсчёт по имени, `os.path.abspath(co_filename)`, два `torch.cuda.Event(enable_timing=True)`, два `record()`, каждый `record()` без аргумента зовёт `torch.cuda.current_stream()` с цепочкой `_get_device_index`, `is_available`, `_nvml_based_avail`, `os.getenv` (1363 чтения `os.environ` за шаг, B5 cProfile). Сэмплер не показывает эти функции в топе (каждая меньше 0,71 мс/шаг, B5:L382), cProfile их раздувает (47,5 мс incl на `current_stream`, B5 cProfile). Реальная цена на запуск на CPU Kaggle не измерена (не проверено). Ноутбук (RTX 5060, WSL, torch из `~/soupenv`, `scratchpad/hbench.py`, 20 000 повторов): то, что обёртка делает сверх самого запуска (abspath, два Event, два record), 36,4 мкс; `torch.cuda.current_stream()` 3,4 мкс; запуск поэлементного ядра torch (`add_`) 10,4 мкс. Под WSL запуски медленнее, чем на Kaggle, поэтому переносится только соотношение: обёртка стоит примерно как 3-4 запуска ядра torch. При 654 запусках это порядка 24 мс CPU на шаг на ноутбуке. Сам запуск Triton-ядра без обёртки там же (`scratchpad/tbench.py`, простое поэлементное ядро) 14,6 мкс против 12,2 мкс у `add_` torch. Итого наш Triton-запуск в замеряемом шаге стоит около 51 мкс CPU, примерно 4 запуска torch. Следствие для слияний (вывод из ноутбучного соотношения, на Kaggle не проверено): заменить k поэлементных ядер torch одним своим ядром выгодно по CPU только при k от 4-5; слияние двух-трёх операций torch в новое своё ядро на CPU-bound участках проигрывает, выигрывает только по GPU-времени и доле своих ядер. Влить операции в уже существующее своё ядро (без нового запуска) выгодно всегда. Харнесс менять нельзя, снизить её можно только числом наших запусков.

## 4. CUDA graphs на этих участках и почему G1 NO-GO

Факты [G1]: шаблон графа MLP на T4 (Modal) снимает 0,29 мс CPU на слой в forward и 0,87 мс в backward; держит +52 MiB allocated / +82 MiB reserved при корзине 512 токенов; захват во время замеряемых шагов невозможен, потому что события TritonWatch внутри захвата становятся узлами графа и `own_ms()` падает с `CUDA error: invalid argument` (ловушка 1); внешние события внутри графа не держат конвейер кольца весов (ловушка 2); потолок 0,2-0,3 с при корзине 512. Ответ 46: графы можно, но ядра в графе не идут в зачёт 5 % своих ядер.

Что добавляет таймлайн B5 (вывод, не измерение): из 1,16 мс/слой, которые снимает шаблон, в стену сейчас может пойти только forward-часть (0,29 мс x 28 = 8 мс на короткий шаг, ~0,09 с за прогон публично), потому что backward коротких шагов упирается в хвост головы, а шаги 600+ GPU-bound. То есть потолок графа MLP на текущем коде ниже оценки G1 (0,2-0,3 с), а память та же +82 MiB при цели 395 MiB. Граф всего forward слоя для коротких шагов снял бы больше CPU, но ловушки 1 и 2 те же, и выигрыш ограничен тем же потолком 0,53 с из раздела 1. Моё мнение: NO-GO остаётся в силе.

## 5. Пересечения

- I1 (CPU-сторона шага): в main нет отдельной заметки I1 по CPU (`docs/notes/i1-int8-fwd.md` про int8 forward). Здесь числа той же зоны; если I1 режет CPU, по разделу 1 стену это двигает только в forward коротких шагов и в начале шага.
- H1 (слияние `floor`/`clamp`/копий и int8-голова): слияние снижает число запусков (CPU и GPU); int8-голова убирает хвост 35 мс в коротких шагах и тем самым делает CPU backward коротких шагов критическим (строка таблицы про backward). Порядок: после H1 повторить cpuprof и смотреть lag backward.
- Второй фронт `claude/b5-fused-quant`: кэш масштабов и слитое квантование уже в данных B5 (на них и построен этот анализ), их не дублирую. Сверх них по CPU остаются: HOST_IDS из C1 (начало шага), пропуск offload-хуков для тензоров, которые остаются на GPU (не проверено), меньше `empty`/view в плане слоя. Каждое даёт порядка единиц мс на короткий шаг, то есть десятые доли секунды за прогон в сумме, не больше потолка 0,53 + 0,12 с.
- Подчат D (хвост и трекер): зазор между шагами 0,37-0,48 с за прогон в основном трекер Soup.
- Проверка вывода про backward на чужом прогоне: ABBA второго фронта `.claude/worktrees/b5-fused-quant/runs_kaggle/20261031-203501-variants-soup-b5-fq-abba` (слитое квантование, минус ~12 запусков torch на слой только в backward; 3 раунда) по корзинам моих токенов: короткие шаги fq минус nofq +5, +8, -7 мс (среднее +2), 600-900 -1, +16, -7, от 900 -12, +11, -16 мс. Срез CPU в backward не дал ничего ни в коротких шагах (backward за хвостом головы), ни в длинных (GPU-bound), как и предсказывает раздел 1.
