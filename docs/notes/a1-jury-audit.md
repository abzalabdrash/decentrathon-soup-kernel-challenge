## 2. Проверка 9 подробно

Невидимый для nvidia-smi пик reserved возможен только там, где память возвращается драйверу (`empty_cache`) меньше чем через ~100 мс после пика: при `expandable_segments` reserved в обучении только растёт. В решении `empty_cache` вызывается в трёх местах: конец настройки стримера весов (`weight_stream.py:645`), откат embed16 (`embed16.py:76`, при стриминге головы не срабатывает) и выпуск при выходе (`exit_release.py:64`, только с `SOUP_SOLUTION_EXIT_RELEASE=all`).

Факты из логов T4. soup-b1-diag2: на всём setup alloc не выше 64 MiB, reserved не выше 106 MiB; после первого шага reserved 190 MiB, nvidia-smi 311 MiB; в обучении 0 освобождений сегментов и 0 повторов аллокатора. soup-codex-r1-jury: «reserved MiB at train begin 50, after step 1 210, max at step ends 272, torch's peak 272». Значит, пик torch всегда приходится на обучение, а не на setup, и nvidia-smi его видит. На длинных строках reserved растёт вместе с nvidia-smi, запас по формуле только увеличивается на 3 % от прироста.

Расхождение, о котором сообщено оркестратору: сообщение мержа ce27a54 говорит «exit release on by default (EXIT_RELEASE=all, EXIT_NOGC=1)», но `solution/__init__.py:117` читает переменную с умолчанием "0", то есть на main выпуск при выходе выключен. Моё мнение: если включать, то `=1`, не `=all`. При `=all` `empty_cache` идёт сразу после последнего шага; если рост reserved пришёлся на последний шаг и прошло меньше 100 мс, nvidia-smi его не увидит. Вероятность мала (между пиком шага и его концом обычно 2–3 опроса), а выигрыш `=all` над `=1` около 0,14 с по замерам E1.
