# I1: политика памяти активаций под фиксированным пиком (закрыто, справочные числа)

Ветка `claude/i1-mem-policy` (от main 2d14d2b). Код: `solution/mem_policy.py` (`SOUP_SOLUTION_MEM_LOG=1` — пик allocated / reserved каждого шага против его числа токенов, печать при выходе; `SOUP_SOLUTION_RECOMPUTE_ATTN=cap` — последние слои держат тензоры attention вместо пересчёта, сколько помещается между предсказанным пиком шага и фиксированным потолком `SOUP_SOLUTION_STEP_CAP_MIB`, решение только по числу токенов шага), точки в `fused_proj.py` (`recompute_layers` режим `cap`, `_fused_attention` вызывает `mem_policy.step_begin`), тест `solution/test_mem_policy.py`. По решению капитана (память строго как есть) **не включается**: всё за переключателями, по умолчанию выключено.

## Модель пика шага (T4, умолчания main: attention пересчитывается во всех слоях)

`soup-mp-pub1` / `soup-mp-jury1` (fbbd2c6), `SOUP_SOLUTION_MEM_LOG=1`: пик allocated шага ≈ **107 + 0,086 МиБ × токены** (публичные: макс. 230 МиБ при 1 440 токенах, reserved 274; строки как у жюри 30000:30256 / 44000:44256: макс. 251,5 при 1 680, reserved 312). Без пересчёта attention: 112 + 0,349 МиБ × токены, то есть каждый слой, держащий attention, добавляет ~10 КБ на токен (0,265 МиБ на токен за 28 слоёв; по формуле `fused_proj._kept_bytes` 10,3 КБ).

## Пересчёт attention против хранения, по корзинам длины шага (ABBA 2 раунда + холостой)

| вариант | публичные: стена / nvidia-smi | как у жюри: стена / nvidia-smi |
|---|---|---|
| base (пересчёт во всех слоях) | 44,71 с / 395 | 55,36 с / 433 |
| без пересчёта (`RECOMPUTE_ATTN=0`, всё хранится) | 44,51 (−0,20) / **769** | 53,45 (**−1,91**) / **855** |
| оффлоад attention вместо пересчёта (N1c, `OFFLOAD_ATTN=1`) | 47,91 (**+3,2**) / 395 | 55,88 (+0,5) / 413 |
| auto (порог 640 токенов) | 44,91 (+0,2) / 479 | 54,71 (−0,65) / 479 |

Без пересчёта против base, мс на шаг (шаги 3+):

| корзина | публичные | как у жюри |
|---|---|---|
| < 600 токенов | −0,9 (11 шагов) | −6,2 (5) |
| 600–900 | +1,9 (31) | −16,4 (15) |
| 900–1 200 | −4,6 (10) | −31,4 (22) |
| ≥ 1 200 | −13,8 (9) | −39,9 (19) |

На публичных строках последовательности короткие и пересчёт дешёвый; на строках жюри длинные последовательности, пересчёт attention растёт ~L² и стоит до 40 мс на длинном шаге. Оффлоад attention (N1c) и при освобождённой P1 шине хуже пересчёта.

## Потолок `cap` (0d27f81), ABBA 2 раунда + холостой

| строки | base | cap 235 | cap 250 |
|---|---|---|---|
| публичные (`soup-mp-pub2`) | 43,66 с / 395 MiB | 43,55 (−0,11) / **395** (allocated макс. 237, reserved 274) | 43,55 (−0,11) / 415 (+20: новый сегмент) |
| как у жюри (`soup-mp-jury2`) | 50,03 / 433 | 50,37 (+0,34) / 435 | 50,54 (+0,51) / 435 |

Под потолком помещается мало слоёв (при 830 токенах 6–8, при 1 200 — 2–3, при 1 440+ ни одного), а длинные шаги, где пересчёт дорог, не имеют запаса; на строках жюри выигрыша нет вовсе (+3…+7 мс на шаг в корзинах 600+, в пределах шума сессии, и +2 MiB nvidia-smi). Вывод: под фиксированным пиком политика активаций не даёт выигрыша; хранение gate|up на GPU (P1: 0 с на публичных) и входов слоёв (ночь: 0 с) тоже. Реальный выигрыш хранения attention есть только без ограничения памяти (−1,9 с на строках жюри за +422 MiB).
