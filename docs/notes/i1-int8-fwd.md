# I1: int8 на тензорных ядрах T4 в forward MLP

Ветка `claude/i1-int8-fwd-784311` от main 8387938. Код: `solution/int8_fwd.py`, хук в `solution/fused_proj.py` (`_int8_forward_ops`, `_int8_forward`, ветка в `_MLP.forward`), метка индекса слоя в `solution/rmsnorm.py` (патч decoder-слоя ставит `mlp._soup_layer_idx`), тесты `solution/test_int8_fwd.py`, бенч `solution/bench_int8_fwd.py` (тайминг, `--sweep`, `--errors` на реальных активациях).

## Схема

Переключатель `SOUP_SOLUTION_INT8_FWD`: как у int8_bwd, по умолчанию включён только в процессе `soup train` (`int8_bwd._soup_train_process`), под pytest выключен (побитовые тесты fp16-пути целы), `=1` включает и там, `=0` выключает везде. Ядра компилирует поток с первого подходящего forward MLP; первые `START_CALLS = 112` подходящих forward (4 шага × 28 слоёв) идут fp16, 113-й ждёт поток, если он не закончил: точка переключения не зависит от таймингов. Считаются только forward с включённым autograd (обучение), no-grad forward (rewind Soup) всегда fp16. Путь берётся только когда MLP хранит (gate|up) для backward (не режим recompute) и веса в раскладке nf4.py.

Режим `SOUP_SOLUTION_INT8_FWD_MODE`:
- **`gu` (по умолчанию)**: int8 только для gate|up. (1) `quant_rows_kernel`: x (M, D) fp32 → int8 по токенам (absmax/127; строки паддинга нули); (2) `nf4_int8_gu_kernel`: W_gate и W_up из NF4 сразу в int8 (2I, D) в естественной раскладке с масштабом на выходную строку, одна программа читает коды absmax своих строк (максимум строки = максимальный absmax её блоков: у каждого блока NF4 есть код ±1), потом распаковывает; без вспомогательных тензоров между шагами; (3) `torch._int_mm(W_q, x_q.t())` → int32 (2I, M), «TN»; (4) `int8_gate_up_kernel`: gate, up = acc · s_w[строка] · s_x[токен] в fp32 → half в (gate|up) (тензор для backward и оффлоада, контракт P1 не тронут) и сразу SwiGLU в half (I, M) для down; (5) down остаётся fp16 GEMM fused_proj на этом выходе.
- `all`: ещё и down в int8 (квантование SwiGLU-выхода по токенам с максимумами по группам признаков из эпилога, транспонирующее квантование `int8_hidden_kernel`, распаковка W_down в int8, `_int_mm`, эпилог `int8_out_kernel`). Численно непригоден (ниже).

int8-веса лежат в общем буфере распаковки fused_proj (int8 gate|up ровно размера одного fp16-веса (I, D)); слоты кольца весов берутся `acquire`/`release` вокруг распаковки. int32-произведение (2I, M) временное, 72 КБ на токен: с ним forward MLP стал пиком прогона (ABBA1: 395 → 475 MiB), поэтому `SOUP_SOLUTION_INT8_FWD_CHUNKS=5` (по умолчанию) делит его на 5 произведений по 2I/5 строк в одном переиспользуемом буфере (14 КБ на токен; строки int8-весов чередуются по кускам: gate куска k, up куска k).

**Разложение top-k каналов** (`SOUP_SOLUTION_INT8_FWD_TOPK=16`, по умолчанию; 0 выключает), как в LLM.int8: 16 входных каналов слоя с наибольшим max |x| идут мимо int8-произведения и добавляются в fp32. Набор каналов фиксируется на весь прогон: fp16-forward до переключения (шаги 0–3) копят max |x| по каналам на модуле (`observe`: один `vector_norm(inf)` и `maximum`, только GPU, без синхронизаций), первый int8-forward слоя берёт `topk` (`channels`). `quant_rows_kernel` выносит эти каналы в x_k (M, 16) fp32 и не учитывает их в масштабе токена; дополнительные программы того же запуска распаковки (`_topk_cols`) пишут fp32-столбцы W_gate и W_up (2I, 16); эпилог добавляет `tl.dot(W_k, x_kᵀ)` до округления в half.

**Ожидание копии**: при раннем оффлоаде fp16-путь ждёт D2H-копию (gate|up) предыдущего слоя (`offload.drain_inflight`) до начала MLP; int8-путь ждёт её прямо перед выделением своего (gate|up), после квантования x, распаковки весов и первого int8-произведения (`before_alloc`), так что копия летит под ними. Пик не растёт: в этот момент живы предыдущий (gate|up) и один кусок int32.

Список fp16-слоёв: `SOUP_SOLUTION_INT8_FWD_FP16_LAYERS` (`0-4`, `1.2.4`, `2,26`; индекс decoder-слоя; MLP без метки считается из списка), по умолчанию пусто.

## Численность на реальных активациях (локально, `bench_int8_fwd --errors`)

Qwen2.5-1.5B-Instruct в NF4 как у Soup (double quant, fp16 compute, нормы fp32, autocast fp16), первые строки `data/train.jsonl` через chat template, по одной строке; каждый MLP считает fp16-эталон (математика fused_proj) и оба int8-варианта на одном входе.

Относительная ошибка (Фробениус) по слоям, 24 строки, 5 847 токенов:
- gate|up: 1,5–2,6 % во всех слоях;
- выход MLP в режиме `gu`: 1,7–4,8 %, кроме слоёв 2 и 26 (30–32 %: токен 0, массивные активации; down на fp16-входе там точен, ошибка от gate|up этого токена);
- выход в режиме `all`: 5–12 % почти во всех слоях: пик/RMS SwiGLU-выхода по токену 45–95, per-token int8 для down теряет мелкие значения; int8 down на точном fp16-входе сам по себе даёт 4,5–11,7 %.

Loss (токены ответа, среднее по строкам; «по строке» = среднее |Δ|/loss по строкам):

| вариант | 24 строки: сдвиг / по строке | 48 строк: сдвиг / по строке |
|---|---|---|
| `all` | +0,87 % / 4,87 % (макс. 28 %) | +1,74 % / 4,33 % |
| `gu` | +0,35 % / 1,12 % | +0,23 % / 1,33 % |
| `gu`, слои 2, 26 в fp16 | +0,63 % / 1,52 % | — |
| `gu`, слои 0–4 в fp16 | — | +0,41 % / 0,80 % |
| `gu` + top-16 каналов в fp32 (эмуляция в torch) | — | −0,04 % / 0,41 % |
| `gu` + top-16 (ядра, `guk`) | — | −0,12 % / 0,41 % (макс. 2,4 %) |

Каналы top-16 выбраны по max |x| первых 4 строк (как «шаг 0») и проверены на всех 48: шум по строке падает втрое, систематический сдвиг уходит. Значит, ошибка gate|up идёт от выбросов x по каналам (пик/RMS по токену 24–33), а не от int8 весов.

Абляция по одному слою (`gu` только в слое L, 12 строк, по строке): слои 1, 2, 4 дают 0,93 / 1,49 / 1,39 %, слой 3 0,64 %, остальные 0,08–0,56 %: шум ранних слоёв проходит больше слоёв ниже. Исключение слоёв 2 и 26 по ошибке выхода MLP не помогает (их вклад в loss не больше соседних).
